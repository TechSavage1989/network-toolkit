NETWORK TOOLKIT UPDATES

ONE-TIME FEED MIGRATION IN REVISED 1.17.63
The revised 1.17.63 build checks the main network-toolkit repository. Installed
1.17.62 clients can download this revised release from their existing feed,
then subsequent checks use the main repository. Review and confirm installation.
If an original63 download is already staged, close and reopen the old app,
then check and download again after revised63 is published. Previously downloaded
ZIPs may still contain the original build despite identical filenames; verify
them against the revised release checksum manifest.

If you already installed the ORIGINAL 1.17.63, the same version number is not
considered newer. Close all app windows and manually replace your application
EXE with the revised Network_Toolkit.exe, keeping its folder, launch options
and --data-dir if used. Keep your settings folder unchanged. The manual update
importer also accepts only newer versions, so it cannot replace same-version
1.17.63. Do not import source-containing Portable.zip as an updater package.

Future updates: open App settings > Updates, choose Check for updates,
then Download update. Once verified, the final Install and restart prompt opens
directly. Its Install and restart button is the final confirmation and starts
installation. There is no extra review action. Export diagnostic results, save
open editor files, and close other Network Toolkit windows first. Active
jobs, terminal sessions, transfers and configuration changes block installation.

Downloads come from https://github.com/TechSavage1989/network-toolkit
The repository contains public source and release assets. The updater downloads
only the strictly allowlisted binary-only Update.zip and SHA256SUMS.
The app does not ask for or save GitHub credentials. Downloads use HTTPS;
SHA-256 checks compare the downloaded ZIP and executable against checksums.
Checksums detect corruption, not a compromised publisher/repository. This
release is not Authenticode signed and Windows may show an unknown-publisher
warning. Only run releases obtained from the official repository.

Installation preserves the app data folder. Update staging, helpers, logs and
one immediately previous executable live under updates in the settings folder.
Each app installation folder has a separate cache. Official names migrate once
to Network_Toolkit.exe and keep that stable name for future updates. Matching
shortcuts in your personal Desktop and Start Menu are retargeted, with original
shortcut backups under settings. Pinned, shared and other-location shortcuts
may need manual retargeting. Custom executable names stay unchanged. Unrelated/manual copies are never removed by filename alone.

The app folder must remain writable. If settings are on a different drive,
short-lived transaction files beside the app allow atomic replacement. They
are removed only after verified transfer to the settings update cache. Locked
or changed files are left pending, with a warning rather than unsafe deletion.
The helper waits for the app to close, replaces it atomically, and restarts with
the same options and working directory. If visible startup cannot be confirmed,
it attempts to restore and reopen the old EXE. update-result.txt and
update-progress.txt record the outcome during installation. The retained
previous.json record keeps a bounded copy of the latest outcome/progress. The previous-version backup is retained
until the next successful upgrade, when it is replaced by the newly previous one.

Recovery: close all app windows. Copy updates/<installation-id>/previous.exe
from the settings folder to the application folder, using its original filename
recorded in previous.json, and use the same launch options/working directory
(including --data-dir). Do not launch the backup from inside settings.
If cleanup is pending, the verified backup may still
be previous.exe in the recorded staging folder. Do not move/delete settings.

Offline/restricted networks: check/download failure leaves the current app
unchanged. Retry later, or use the optional official ZIP + SHA256SUMS import.
Only newer stable Windows x64 releases can be staged. Do not mix files from
different releases. Downloading does not install until you confirm restart.

AUTOMATIC REMINDERS (1.17.59 AND LATER)
From 1.17.66, the main Windows window checks after startup and every five minutes
while visible and online. Returning to the app can check after two minutes since
the last attempt, unless a retry or service cooldown is pending. Hidden/offline
windows pause periodic checks. This is polling, not push notification delivery.
The update banner asks before downloading; a verified download then opens
the final Install and restart prompt directly. Staged updates in the banner
and App settings use one Install and restart click, without another dialog.
Save your work before clicking it. Nothing is
automatically downloaded, installed, or restarted. Later hides that reminder
for 24 hours. Use App settings > Check for updates to show it sooner.
Automatic checks can be disabled in App settings. Quiet network failures retry
after 30 seconds and 2 minutes, then back off from 15 minutes to six hours.
App settings shows the last automatic result and next check. GitHub service
cooldowns apply to manual checks too. Conditional requests reduce bandwidth,
but unauthenticated checks still share GitHub's per-IP request limit. Multiple
app instances or other apps on that IP may delay detection. No credentials or
notification permissions are required. Cached release details survive temporary
errors and valid not-modified responses; no cached response authorizes installation.
Updates apply only to the executable. Saved settings/profiles are retained.

1.17.62 BOOTSTRAP AND DIAGNOSTICS
The initial update is performed by the currently installed version's helper.
An older helper may initially create a sibling .network-toolkit-update-* folder.
The new app migrates verified backups and removes managed artifacts only after
successful install confirmation and the helper has exited. Future updates stage
in settings and directly launch the stable name. No full compatibility
launcher chain is retained. During the first migration, a one-time final reopen starts the current
stable EXE after the old process exits, preserving elevated-tool identity.
The visible-window readiness fix and 90-second startup timeout are preserved.
No native Windows updater execution was available during build validation.

The legacy .network-toolkit-current.json pointer is removed only after a healthy
stable-name relaunch and safe shortcut/alias cleanup. This build never creates
a new pointer beside the EXE. A collision with an existing Network_Toolkit.exe
is preserved, never overwritten. Close other copies and resolve the collision
before retrying migration. Unverified/changed legacy files are preserved.
