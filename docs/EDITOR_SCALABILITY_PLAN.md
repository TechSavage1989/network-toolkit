# Text Editor scalability

Owner requirement (2026-11-08): the editor must work effectively with text files of any size without making opening, scrolling, typing or the rest of the app laggy. This supersedes the bounded-file acceptance criteria for the unpublished v1.21.20 Beta 1 candidate. PR #139 remains a draft until the full replacement is implemented and verified.

## Design

- Keep large documents in a private disk-backed buffer. A balanced piece tree records byte, UTF-16 and line counts; it stores offsets into an append-only file rather than copies of the document.
- Undo and redo retain tree roots and edit fragments. They do not copy the entire source for every keystroke.
- Load only a bounded viewport into the renderer, with nearby pages prefetched. Long single lines must also be paged; DOM size and input work must not grow with total file length.
- Run import, indexing, search, comparison and save outside the UI thread, with progress and cancellation. Opening and saving still require physical disk or network I/O; zero time for unbounded input is not a possible guarantee.
- Save from a stable buffer revision using a temporary file, preserve encoding and line endings, detect external changes, and retain explicit overwrite consent. Newer edits made during save remain dirty.
- Move document handles between windows under the existing owner/lease protocol. Never send a full multi-gigabyte document or undo history in a recovery checkpoint.
- Preserve local and supported remote editing, split views, comparison, search, selection, undo/redo, Save As and dirty-close safeguards. A partial viewport must never be saved as if it were the complete file.
- Comparisons use streamed, paged results. They must not inherit a file-size or line-count ceiling from the current renderer or quadratic diff matrix.

## Verification

Use generated fixtures only. Cover UTF-8, BOM-marked UTF-16LE/BE, CRLF/LF/CR, Unicode at page boundaries, extremely long lines, millions of short lines, scattered edits, undo/redo, save while typing, external modification, cancellation, window ownership and recovery.

Measure 16 MiB, 256 MiB and multi-gigabyte files. Record open/index progress, viewport request latency, input-to-paint latency, UI long tasks, memory use, exact saved bytes and checksums. Interactive memory and work must depend on the viewport and edit history, not repeated full-file materialization. Initial indexing, whole-file searches and saves may take time proportional to bytes processed, while the app remains responsive.

## Current status

- Existing candidate: reduces repeated gutter rendering and large comparison work, but still uses full strings, full-state checkpoints and fixed input limits. It does not meet the revised requirement.
- Implemented foundation: disk-backed persistent AVL piece tree; bounded UTF-16-position windows; fragment edits; undo/redo; streamed UTF-8/UTF-16 import and save; cancellation; existing document lease integration; local overwrite/conflict checks and staged remote save. Search streams from a tree seek and preserves document/word-boundary context at a nonzero cursor. Reload retains the old buffer until a replacement imports successfully. Mutation request identities make lost acknowledgements safe to retry.
- Renderer components: a bounded page session coalesces typing, retains unacknowledged text, rejects stale viewport replies, and preserves newer edits after an earlier save completes. An isolated textarea view supports paged navigation, virtual line scrolling, large offsets, undo/redo and a long-line position control. The modules are loaded but **not connected to normal application documents**; `editorDiskAvailable` is deliberately not advertised by the backend yet. Existing application file-size and comparison limits remain until that integration is complete.
- Verified locally with generated fixtures: randomized editing/undo/redo, Unicode and encoding boundaries, extremely long lines, 64 MiB exact saved content, ownership transfer, stale-lease rejection, Save As consent and external modification. All application packages compile. Hosted Windows native regressions remain required.
- Engine benchmark, Windows synthetic fixtures: 256 MiB imported in 2.247 seconds with approximately 0.319 MiB retained Go heap; 2 GiB imported in 19.571 seconds with approximately 2.521 MiB retained Go heap. The same batch of 100 edits plus 100 viewport reads took 33.6 ms and 40.9 ms respectively. These measurements exclude UI, network transfer, OS cache and disk storage; they are not end-to-end application latency claims.
- Isolated browser fixture: an 8 GiB logical document (generated by offsets, not an 8 GiB physical file) navigated to line 1,000,001 and EOF, edited, undid/redid and saved. The final viewport contained 4,100 UTF-16 units and 24 gutter nodes; edit requests contained one character each; that local run recorded no browser tasks over 50 ms. This does not establish application, disk, native-window or network performance. Script: `scripts/editor-disk-view.browser.cjs`; generated reports/screenshots remain under ignored `test-results/`.
- Additional synthetic regressions cover remote staged-save conflicts, stale transports, typing during a blocked remote upload, failed reload, lost mutation acknowledgements, stale view replies, Unicode windows, nonzero search anchors and later edits surviving a delayed save response. The new package, focused race checks and isolated browser fixture are included in hosted Checks; the package is also part of the release test gate.

## Remaining integration work (publication blockers)

1. Route local, remote, browser-imported and growing Untitled documents through the new storage path without exposing a truncated page to a legacy full-string action. Keep small-document behavior and explicit save/overwrite consent.
2. Connect the viewport to single and split editors, status, search/replace, selection, clipboard, terminal insertion/export, save/reload and close guards. Finish cross-page selections, IME, scrolling/prefetch and long-line acceptance in the actual app. Large inserted text requires a streaming/transactional bulk-edit path; the current per-request fragment bound is not a document-size limit.
3. Connect handle-only recovery and moves through `editor-windows.js`, drain pending edits before handoff, and confirm crash/close/restart behavior with the existing ownership tests. Do not expose a partially integrated feature by setting the capability flag early.
4. Replace full-string comparison and its 16 MiB/30,000-line ceiling with streamed/paged comparison. Test both inputs independently and preserve compare/split actions.
5. Measure real end-to-end generated 16 MiB, 256 MiB and multi-GiB files; verify saved bytes and responsiveness during background operations. Run both push and PR Checks, including hosted native fixtures, before the guarded release process.

No unrestricted-size support is claimed until these paths are complete. PR #139 remains a draft; do not merge or publish based on component benchmarks.
