# Shared app data

Settings and saved data are shared by every Network Toolkit app that uses the same data folder: the main window (the portable program and the installed one), the standalone Terminal and the standalone Text Editor. A connection saved in one app is there in the others; a setting changed in one takes effect in the others. This note describes where the data lives, how saves from several running apps are combined, the one-time migration, and what happens when something fails.

## What is shared

| Shared by every app | Where |
| --- | --- |
| Saved and recent connections (terminal, FTP/FTPS, SFTP), manual order, learned prompt names, verified SFTP fingerprints | `Network_Toolkit.settings.json` in the data folder |
| Settings: theme and accent, color picker and diagnostic colors, all Terminal settings (appearance, highlighting rule sets, features, mouse and keyboard, font size, confirmations, sidebar side), Text Editor preferences and its file sidebar, time format | the same file |
| Saved credentials | `Network_Toolkit.credentials.v2.vault` (one vault per data folder) |
| Trusted SSH host keys | `Network_Toolkit.ssh_known_hosts.json` |
| Macros and startup macros | `Network_Toolkit.macros.json` |
| Open editor tabs and kept copies of unsaved text | `Network_Toolkit.editor-session/` per editor workspace, taken over by the other editor when its app is not running |
| A copy of the saved lists (for the case that an older version saves over them) and of every key only the main window uses (for writing a settings file that went missing) | `Network_Toolkit.saved-lists.json` |

The portable and the installed program already used the same data folder (`%LocalAppData%\NetworkToolkit`, or the folder chosen under **App data**; see `storage_location.go`). The standalone apps now use that folder's files too, instead of copies in `Network_Toolkit.Terminal/` and `Network_Toolkit.TextEditor/`. Those workspace folders hold only what is about one window.

**The key table.** `sharedDataKeys` in `cmd/network-toolkit/shared_data.go` lists every shared settings key with how it is merged; `perWindowStateKeys` lists every key that stays with one window. A key in neither table is treated as per-window, and `TestSharedKeyTableClassifiesEveryPageKey` and the browser check fail until it is classified. Classify a new key as shared if the user sets it on purpose, and as per-window if it is about one window or one run.

Per-window (each window keeps its own): the active page and selected tabs, which panels are open or collapsed, panel and sidebar sizes, the pane layout, form drafts and inputs (the connection form, diagnostic forms, calculators), current filters and searches, the first-launch marker, update reminders, and one-time upgrade markers. Keys marked `MainOnly` (saved diagnostic targets, saved result filters, TFTP profiles, file-server settings, chosen result columns, the Overview layout) are shared between the portable and the installed main window; a standalone app neither receives nor writes them.

## Saving from several apps

Each page keeps all its settings in memory and saves all of them. A save is therefore never taken as the new truth.

1. The page remembers the shared values it and the engine last agreed on. With a save it sends, in `_sharedBase`, the earlier value of every shared key it changed. Keys it does not list were not changed by it.
2. The engine takes the data folder's lock (`Network_Toolkit.credentials.lock`, the lock earlier versions already used for the settings file), reads the settings file as it is now, and for each changed key merges three ways: the page's value, the value the page started from, and the value on disk.
   - **Lists of entries with an id** (connections): entries the page added, removed or changed are added, removed or changed on top of the list on disk. An entry changed on both sides keeps the page's version. A change beats a removal, so an edit is never dropped. The page's order is used if the page reordered the list. An entry without a usable id (none, or one that another entry of any of the three lists also has) is told apart by its content instead, so such a list is still merged entry by entry and never as "the page's whole list wins".
   - **Settings objects**: merged member by member, with the same rules. Two apps that change different options of one dialog both keep their change.
   - **Single values**: the page's value is taken only if the page changed it.
3. The result is written with an atomic replace. If it differs from what the page sent, the answer carries the merged values and the page applies them.

Every 2.5 seconds, while its window is visible, a page asks `GET /api/shared-data?revision=…`. If another app changed something, it gets the current values of the keys marked `Live` and applies them: lists are redrawn, the theme, Terminal settings and editor preferences take effect at once. A change waits while the user has unsaved changes, an open dialog or menu, a drag, or is typing in a field it would redraw. Keys not marked `Live` are read when a page starts.

A client that sends no `_sharedBase` is taken to have started from what the engine last served to it or accepted from it.

**Lists are never cut short.** Because a list is merged by entry, a page that sent a shorter list than it was given would be read as "the user removed these". The key table therefore gives every list one of two rules, and the page (`SAVED_LIMITS` and `ROLLING_LIMITS` in `web/assets/shared-data.js`) uses the same numbers; `scripts/shared-list-limits.test.cjs` compares them and fails on any page statement that shortens a saved list.

- A **saved list** (`MaxSaved`: saved sessions 200, saved FTP connections 200, saved targets 200, saved TFTP profiles 100) is loaded whole and saved whole. No sanitizer and no load path shortens it, even when it holds more than the number. When it is full, the page refuses another entry in plain words and changes nothing. If two apps add at the same moment and only one entry fits, the engine saves the first, leaves the other out, and tells that page which entry was not saved (`sharedData.refused` in the answer); the page removes it from its list and says so.
- A **rolling list** (`Limit`: recent connections 50, learned prompt names 200) keeps its newest entries; the oldest leave on their own.

The 2 MiB limit of a settings file is unchanged, as are all sanitizers; they run on the page's values, on the earlier values it sends, and on what is read from disk.

## Other shared stores

- **Credential vault.** One vault per data folder, bound to the configuration identity in the data folder's settings file. Unlock rules are unchanged: a master password, a remembered unlock for this Windows account, or the no-master-password mode. A vault file another app saved is taken over only if it is the same vault generation and authenticates with the key this app already holds; otherwise the app starts over from the files on disk, as at start (locked unless a valid remembered unlock exists). A save that finds a newer vault redoes its change on that vault.
- **SSH host trust.** Every check and every change reads the trust file again if it changed, and changes are made under `Network_Toolkit.shared-data.lock`. A decision made in another app while a prompt was open is never replaced. While the trust file cannot be read, SSH is refused (trust is never guessed or reset); the next use reads it again, so one failed read does not last. A trust file that was unreadable when the app started needs a repair and a restart, as before.
- **Macros.** The library keeps its revision check; a save is read-compare-write under the same lock.
- **Editor sessions.** Each process that uses its editor session holds a shared lock on `Network_Toolkit.editor-session.lock` in its workspace. An editor that restores its session takes over the other workspace's tabs only if it gets that lock exclusively (and no older version's window answers). A tab's record leaves the other index only after this index holds it; a kept copy is removed there only after it exists here. A file open in both with unsaved text keeps both versions.

  "Reopen files next time" (`editorPreferences.restoreSession`) is a shared setting, so it can be off in an app whose last run kept unsaved text, and it can change while an app runs. Kept text is never left hidden and never removed unseen:
  - An app that starts with the setting off still reads its session and reopens every document with unsaved text, once (saved files are not reopened). After a document is open in the window, its kept copy leaves the session and closing asks as usual.
  - When the setting goes off while an app runs (here or in another app), the kept copies of the documents open in that window leave the session; records that could not be reopened stay. Switching it on again keeps those records too.
  - The engine enforces this whatever a page does: until a run has been given the session (`GET /api/editor-session`), it removes only kept copies that run wrote itself and refuses (409) a save or delete that would drop the record of any other kept copy. After an unreadable index was set aside, deleting the session keeps that index and the copies it may name.
- **Tabs handed to the Text Editor app.** Popping the main window's editor out while the standalone Text Editor of the same data folder runs hands its local and untitled tabs to that editor (`peer_handover.go`, `editor-handover.js`). The main window keeps each tab read-only until the Text Editor confirms it; with "Reopen files next time" on, the Text Editor confirms a tab with unsaved text only after its own session holds a kept copy of it. Only then does the main window release the tab, and its own session drops it at its next save. A tab that is not confirmed stays in the main window unchanged; if the Text Editor opened it but its confirmation was lost (it closed, or did not answer within a minute), both windows have it, never neither. Undo history is not handed over.

## One-time migration

At start, `migrateSharedData` (`shared_migration.go`) adds what the standalone workspaces kept for themselves to the data folder:

- Connections and macros the data folder does not have are added. One with the same id but different content is added as a second entry named "… (Terminal)". Nothing in the data folder is overwritten. Entries of a workspace that share an id with each other are each brought over with an id of their own. A list stops at its limit in the key table; what did not fit is named in a notice and added at a later start once there is room. A part that could not be brought over is not recorded as done.
- A setting that differs keeps the data folder's value; a setting only the workspace had is taken over. Highlighting rule sets written in the standalone window are kept next to the data folder's.
- Two Text Editor settings are the exception, because they decide what happens to unsaved text: for "Reopen files next time" and "Ask before closing unsaved documents" the safer value (on) wins when the data folder and a workspace differ. This is decided once per workspace, so a later choice of the user stays.
- Trusted SSH hosts are united. If the two had different keys for a host, the data folder's key stays, the other is not trusted, and the user is told which hosts to check. Hosts that only a workspace trusted are trusted by every app afterwards; the user may have removed one of them in the main window on purpose, so a notice lists them and says where to remove a host (Saved sidebar, SSH host keys).
- Credentials are not moved automatically (the previous vault may have another master password). The password manager offers **Import saved credentials from the previous Terminal vault**; see `credential_vault_import.go`. If the shared vault is full, the credentials that did not fit are named and the import stays on offer until all of them are in.

The workspace files are only read and stay where they are. Each data-folder file is copied once, untouched, before its first change (`Network_Toolkit.before-sharing.*`). `Network_Toolkit.shared-data.json` records what was handled, so a repeated run does nothing and an entry the user later removes does not come back. If an older version of the app later changes a workspace file, only its new entries are added.

## When something fails

- **A crash during a save**: every file is replaced atomically; the previous file stays until the new one is complete.
- **A file is read while another app replaces it** (every poll does this): the reader gets the old file or the new one, never half of either. `internal/sharedfile` and the retrying readers (`readCredentialFile`, `readStorageFile`) wait out the two things that can go wrong for a moment: the file that was opened is not the one that was inspected (the replace happened in between; the read is made again and checked in full), and on Windows a file cannot be replaced while another program has it open. Shared files are therefore opened for reading with `FILE_SHARE_DELETE` (Go's `os.Open` does not pass it) and, when a plain replace is refused, replaced by a rename with POSIX semantics, which Windows allows over such readers; for a reader that did not allow it (a scanner, an older version of the app) the replace waits briefly and tries again. In the instant in which a file is renamed into place, Windows in turn refuses an open that does not allow deletion; this app's own readers are not affected. The lock file of the settings is created without sharing by the first app that needs it; finding it unopenable is treated as finding it locked. A read that fails is never taken for "the file was reset": the vault locks only after the settings file was read and shows another identity (or none, or is gone); a trust file that cannot be read refuses SSH for as long as that lasts and no longer.
- **A crash during the migration**: each part can be repeated. The next start completes it and adds nothing twice.
- **One part of the migration fails** (for example a damaged macro library, or a settings file that cannot be written): the other parts are done, the failure is logged, and the part is tried again at the next start. What a part handled is recorded only after its file was written.
- **The data folder's settings file is gone** (while apps run, or when one starts): that is not read as "another app removed everything". A running app keeps what it shows. Whoever writes the file next writes everything it holds and takes the rest from the copy (`recreateRootLocked`, called by every writer; `readSharedSettings` fills a missing file from the copy first). In detail:
  - *The copy is newer than a running app that has not refreshed.* The copy is written before every save of the file, so it is at least as new as the file an app last read. A running app therefore merges the copy into what it holds before it writes (`absorbCopyLocked`: three ways, on the base of what its page was last given), and an entry another app removed or added since stays removed or added. Nothing is removed when what the app holds is in no file at all or came from a file an older version wrote.
  - *An app that starts without the file* starts from the copy. Its first refresh writes the file again.
  - *The user is told.* Whenever entries come from the copy, a notice ("Saved entries were recovered") names them once the file is written.
  - *No copy either, or a copy that cannot be read.* A standalone app holds nothing of what only the main window uses. It still writes what it holds (a refused save would leave that nowhere but in its memory, and would leave saved credentials unusable, because their identity is kept in this file) and, if it saw a settings file earlier in this run, puts `sharedMainOnlyAbsent` into the file: the main window's keys are absent, not removed. In a data folder that never had a settings file nothing is absent, and no note is written. A main window that is running keeps its own and removes the note with its next save or refresh. A copy that could not be read when an app started is taken in as soon as it can be read, before the app's first write.
  - *The file was written anew by an app that could not know what this one holds* (a main window that started with nothing writes empty lists). A running app notices this in three ways: it saw the file missing, it still holds values that are in no file, or the file carries another id than the one it knew (the value of the mark, see "The copy is paired" below). It then reads nothing in that file as removed: it adds what it holds (list entries and object members the file lacks; single values as it holds them) and saves that with its next refresh (`keepHeldLocked`, `dirty`, `saveHeldLocked`). That happens once: what the file lacked is remembered per key (`heldExtra`) and stays pending until a save of this app has written it. From then on a later change of the file is read as it is, with only those pending values added, so a removal another app makes meanwhile is accepted and nothing this app holds is dropped. The refresh waits only a quarter of a second for another app that is saving. If the save fails, the reason is shown as the app's storage error for as long as values are pending, and the save is tried again: after 2 seconds, then twice as long each time, at most once a minute, and at once when the settings file changes. The values are never given up.
- **The copy of the saved lists, or its id file, cannot be read or written**: the settings file is the user's data, the copy and the id are protection, and a problem with the protection never stops a save (`writeSharedSettings`). The settings are saved; a copy or id file that could not be read is left exactly as it is; the user is told once, in plain words, which file is the problem (`protectionProblem` in the answer of `GET /api/shared-data`). The settings file then carries `sharedCopyBehind`:
  - `"read"`: the copy could not be read when it was needed (the settings file was missing, was written by an older version, or already carried this note), so it may hold saved entries the file lacks. The file is served and saved as it is. As soon as the copy can be read, a reader puts back what the file lacks: saved entries, and what only the main window uses, merged under the file's values member by member (what the file has wins, what only the copy has is restored, and an empty object that a main window saved as its default does not hide the copy's members). This happens before the copy is written again, because the copy is the only place that still holds them, the next refresh or start writes that, and a notice names the entries. An entry removed in the meantime comes back with them; the notice says so.
  - `"write"`: the save knew everything and only could not write the copy. The file is the truth; nothing is put back. A refresh tries the copy again after 2 seconds, then twice as long each time, at most once a minute, and at once when the settings file changes; a save of the user's writes it as well. A settings file that would be the same byte for byte is never written again, so while the copy stays unwritable the settings file is left alone. The note is removed once, with the save that wrote the copy.
  - An id file that cannot be replaced because something else is in its place (a folder) still counts as there: the copy stays paired. When the id cannot be kept at all (`Network_Toolkit.Views` is a file), the copy is written without an id and used as v1.21.40 used it. The id in the settings file's mark stays the same in every case.

- **The settings file cannot be read**: pages keep what they show. A file that could not be read at that moment (for example while another program holds it) is never replaced; the save is refused and tried again. A file that is not valid is replaced only by the main window, with everything it holds, as before; a standalone app refuses to save over it and reports the problem.
- **Another app holds the lock**: a save waits up to five seconds, then reports that another app is saving.
- **An older version runs on the same data folder**: see the next section.

## Older versions on the same data folder

A portable copy and an installed copy are updated separately, so a version from before shared app data (v1.21.38 and older) can meet a data folder this version uses. What such a version does, from its code:

- Its engine reads the settings file once, at start, and never again.
- Its page keeps only the keys it knows (any other key is dropped with its next save) and at most the first 100 saved sessions and the first 100 saved FTP connections.
- Every save writes all of that back: no reading, no merging. It takes the same lock file, so it never writes in the middle of another app's save.
- Its standalone Terminal and Text Editor read and write only their own workspace folders.

**Saved entries are never dropped for good.** `shared_older_version.go`:

- Every save of this version puts the mark `sharedDataWriter` into the settings file. An older page drops it, so a settings file without the mark was last written by a version that does not merge. The value of the mark is the id of the file (v1.21.40 wrote `1`).
- Every save of this version first writes the saved lists (saved sessions, saved FTP connections, saved targets, saved TFTP profiles) to `Network_Toolkit.saved-lists.json`, then the settings file. `writeSharedSettings` is the only function that writes the settings file.
- A reader that finds the settings file without the mark (`readSharedSettings`, used by every read of shared values) puts back every entry of that copy that the file no longer has. Entries the file has always win; entries that are put back follow them. The next save of this version, or its next start (`migrateSharedData` repairs the file before a page is served), writes them to disk again, and the user gets a notice naming them.
- A settings file with the mark is taken as it is, whatever the copy says: this version writes the whole file, so after an interrupted save the settings file is the truth.
- Whether an app has already taken in a settings file is decided by a digest (`rootSettings.digest`). For a file without the mark the digest covers the file together with the saved lists after the put-back: an older window can write the very same bytes twice while an app of this version added or removed an entry in between, and the result of reading it is then a different one. The notice names only entries that the save really wrote.

This design was chosen over keeping only 100 entries in the settings file and the rest in a second file. That split still loses an entry that moves from the second file into the first 100 (after a removal or an edit in this version) while an older window, which loaded before that, saves what it holds. Putting back every missing entry has no such gap. Its price is that the two cases below cannot be told apart from "the older version never saw this entry".

**The copy is paired with its settings file.** An older version does not know the copy. Its "Delete app data", or a move of the data folder without copying, removes the settings file and leaves the copy, and a copy alone cannot say whether its settings file was lost or deleted. So the same id is kept in three places: as the value of the mark in the settings file, as `pair` in the copy, and in `Network_Toolkit.Views/00000000000000000000000000000000/Network_Toolkit.window.json`. That third place was chosen because every version since v1.19.1 removes the window state of every detached view with "Delete app data", no version touches it otherwise, and no real view has that name. Rules (`usableSavedListsCopy`, `writeSharedSettings`, `settleSavedListsCopy`):

- A copy is used, to put entries back or to write a missing settings file, only when its id is the one in the third place. A copy from v1.21.40 has no id and is used as that version used it.
- A copy whose id is not there belongs to data an older version deleted. It is never used, and the next start removes it, which completes that deletion. Exception: when the settings file carries the same id (a data folder that was copied by hand without `Network_Toolkit.Views`), the id is written again instead. A move by this version takes the id along, when the move is chosen and again when the app closes (with the other files of a pending move). A move is never refused for the id file: when it cannot be read, is damaged or cannot be written at the new place, the move goes on without it, and because the moved settings file carries the same id, the next start at the new place writes it again.
- A save keeps the id of the settings file it replaces, whatever can be read of the copy and the third place at that moment. Only a settings file that is missing or has no id (an older version or v1.21.40 wrote it) gets its id from the copy and the third place, when they agree, or else a new one.
- **"Does not exist", "could not be read" and "was read and says otherwise" are three answers** (`readProtectionFile`, `readSavedListsCopyState`, `readSavedListsWitness`, `usableSavedListsCopy`). A copy is ignored or removed only when its id is confirmed to be absent or another one. "Does not exist" includes a path below something that is not a folder (ENOTDIR; on Windows `ERROR_PATH_NOT_FOUND` and `ERROR_DIRECTORY`). Something that is not a regular file in the file's place, or contents that are not what is expected, is "was read (damaged)": a damaged id file was not removed by a deletion, so the copy counts as paired and the id is written again when that is possible. Everything else (access denied, a sharing or lock violation after the retries, an I/O error) is "could not be read" and decides nothing: the copy is neither used nor written over nor removed, saving goes on as described under "The copy of the saved lists, or its id file, cannot be read or written", and the start leaves everything as it is and looks again next time.

What this cannot tell apart:

- *An older version's deletion from the loss of both the settings file and the `Network_Toolkit.Views` entry.* If both go missing for another reason (deleted by hand, a restore that skips the folder), the saved lists are not recovered from the copy.
- *A deletion by an older version while a copy from v1.21.40 is in place.* Such a copy has no id, so it is used: the deleted entries come back once, as in v1.21.40. The first save of this version gives the copy its id.
- *A deletion by an older version while an app of this version is running.* That app keeps what it shows and writes it again, as it does for any settings file that goes missing under it.
- *A settings file deleted by hand from a lost one.* The copy and its id are still there, so the saved lists come back, with the notice. To reset, use **Delete stored app data**.
- *An older version that saved over the settings file after the `Network_Toolkit.Views` entry was removed by hand.* The copy counts as left over from a deletion, so what that older version dropped is not put back.

While an older main window is open, every running app of this version says so once (the settings file lacks the mark; `olderVersion` in the answer of `GET /api/shared-data`). That is only known after the older window has saved something.

**What an older standalone app adds later is picked up.** Its workspace files are examined again at every start of this version when they changed. Saved sessions, FTP connections, macros and trusted hosts that are new are added; an entry or host the user removed in this version is recorded per id in `Network_Toolkit.shared-data.json` and does not come back.

**What remains unprotected while an older version is in use:**

- A saved entry removed in the older version comes back (it is named in the notice; remove it again in this version). A saved entry removed in this version while the older main window is open comes back with that window's next save, because it still holds it.
- An edit made in this version to a saved entry that the older main window also holds is replaced by that window's version with its next save.
- Settings, recent connections, learned prompt names and verified SFTP fingerprints go back to what the older main window holds with each of its saves, until it is closed.
- Trusted SSH hosts: an older main window writes the whole trust file from what it loaded at start. A host trusted elsewhere meanwhile is asked about again; a host removed elsewhere meanwhile is trusted again without a question.
- An older standalone app does not see what was saved since the one-time move, and what was removed in this version is still in its own copy.
- Saved credentials of an older standalone app stay in its own vault until they are imported.

Update every copy of the app to end all of this.

Moving the data folder and deleting app data cover the three workspaces of a data folder (the folder itself, `Network_Toolkit.Terminal` and `Network_Toolkit.TextEditor`; `storageWorkspaces` in `storage_location_files.go`) and include the shared files, the copy of the saved lists and its id, the migration record and the untouched copies. Deleting therefore removes everything the one-time migration reads, so the next start brings nothing back and trusts no host again. Credential vaults are never deleted with app data. Both are refused while another app of the data folder is running.


## A save that is refused

A save of the settings is refused only when writing could destroy something or cannot work:

- another app of the data folder holds the settings lock for more than five seconds ("another app is saving");
- the settings file itself could not be read at that moment, or (for a standalone app) is not valid: writing over it could destroy what another app saved;
- the settings file could not be written (disk full, access denied), or the settings exceed 2 MiB.

The page does not leave it at one attempt (`retrySave` in web/index.html): it tries again after 1 second, then twice as long each time, at most every 30 seconds, and shows "Your last changes are not saved yet … keeps trying" until a save has worked. That message is shown only while a retry is scheduled: a retry that comes due while the engine is not connected or the settings have not loaded is scheduled again, and one that comes due during "Delete app data" removes the message. A save that can never succeed as it is (a 400 answer: settings over 2 MiB or not valid; or the display-name refusal, which the engine marks with `code: "settings-reload-required"`) is not retried; the message then says "Your last changes are not saved", and the user's next change is saved as usual. Closing the app tries the save for about two seconds with one message for the round, and the closing save (`PUT /api/state?closing=1`) waits only half a second for another app, so the question reaches the user well inside the five seconds the host window waits for a close; if it still fails, the app does not stop silently: the user chooses **Try again**, **Close anyway** or **Keep open** (`saveBeforeClose`). A save that can never succeed is tried once at close and asked about once per session (without **Try again**). Native window close reaches the same code through `window.__networkToolkitClose`. The host window has no way to learn that a page dialog is open: as with the prompts about unsaved documents, it shows its own "Close not approved" box when the page has not closed within five seconds, and the app stays open. The prompts about unsaved documents come first and are unchanged. Nothing is asked when nothing could be saved (the settings never loaded, the engine is not connected).

## Known limits

- While the copy of the saved lists cannot be written, it does not protect against an older version: an entry saved in that time and then dropped by an older version's save is not in the copy. The user has been told that the copy cannot be written.
- After the copy could not be read for a while (`sharedCopyBehind` is `"read"`), an entry the user removed in that time comes back with the put-back, named in the notice.

- A settings file that is deleted by hand while its copy stays is treated as lost, not as a reset: saved lists and main-window settings come back from the copy, and a notice says so. To reset, use **Delete stored app data**, which removes both.
- The copy holds the saved lists and the main-window keys, not the other shared settings (theme, Terminal and editor settings, recent connections). If the settings file is lost while no app is running, those start from their defaults. If it is lost while an app runs that has not refreshed, that app writes those settings as it holds them, which can be older than what another app saved last.
- When neither the settings file nor a usable copy is left and no main window is running, what only the main window uses (saved targets, TFTP profiles, result filters, layouts) is gone: no app holds it. A standalone app still saves what it holds.
- An app that adds back what it holds to a settings file that was written anew can bring back an entry that another app removed after this app last refreshed, and its own single settings win over those in the new file. This happens once, with the first refresh after the file was written anew.
- An app notices a file that was written anew behind its back (it never saw the file missing) by the id in the file. A data folder in which this version has not saved yet has no id; there, an app that did not refresh while the file was missing takes the new file as it is.
- With v1.21.40 on the same data folder, the copy loses its id with each of that version's saves; the next save of this version writes it again under the same id. If the `Network_Toolkit.Views` entry is missing at that moment, the file gets a new id and running apps of this version add back what they hold once.
- The untouched copies from before sharing (`Network_Toolkit.before-sharing.*`) and the migration record are unknown to older versions too, so an older version's "Delete app data" leaves them. They are never read back into the app; this version's "Delete app data" removes them.
- A save holds the app's own state lock and the data folder's settings lock while it replaces up to two files (the copy of the saved lists and the settings file). Other requests to the same app that need its settings wait for that; on Windows a replace can itself wait up to 1.5 seconds for a program that holds the file. Notices are written after both locks are released.
- The macro library is merged by revision, not by entry: of two apps that save at the same moment, the second is refused and its page loads the library again.
- A transient failure to read the settings file is retried and never taken for a reset, but while it lasts saved credentials are refused and saves answer "try again".
