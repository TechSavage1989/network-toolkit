# Network Toolkit standing instructions

## Authority and scope
Read [docs/UX_POLISH_PLAN.md](docs/UX_POLISH_PLAN.md) first. It is the owner's authoritative UX plan; follow [docs/DEVELOPMENT_ROADMAP.md](docs/DEVELOPMENT_ROADMAP.md) for phase status. Historical plans in docs/archive/ are not active requirements. Read docs/DEVELOPMENT_HANDOFF.md for current progress.

**Never prepend release records to AGENTS.md or README.md.** Keep release history in CHANGELOG.md and per-release technical evidence in docs/releases/ or existing docs/RELEASE###_HANDOFF.md files.

## Working with the owner
- The owner has given standing approval to publish new betas when their required release checks pass. Proceed through publication and verification without asking for release confirmation again.
- When the owner's input or decision is needed, when a release has been published, or when work is waiting on the owner, start that message with a bold, clearly marked line (for example **⚠️ ACTION NEEDED:**, **✅ PUBLISHED:** or **⏳ WAITING ON YOU:**) so it cannot be missed (owner request, 2026-11-07).
- End every message to the owner with a clear status: what is done or published, what is running and roughly when it finishes, and what (if anything) the owner needs to do (owner request, 2026-11-07).
- Terminal settings modeled on MobaXterm are planned in [docs/TERMINAL_SETTINGS_PLAN.md](docs/TERMINAL_SETTINGS_PLAN.md).

## Owner's non-negotiables
- Text Editor scalability (owner clarification, 2026-11-08): work effectively with text files of any size while keeping interaction and the rest of the app responsive. Fixed 16/32 MiB file and 30,000-line limits do not meet this requirement. Follow `docs/EDITOR_SCALABILITY_PLAN.md`; do not publish the current bounded-file candidate as completing it.
- Never lose credentials, vault entries, saved profiles, preferences, macros, unsaved work or active sessions. Migrate settings explicitly.
- Preserve Windows/UAC authorization, Hosts/IP/adapter review, explicit download and install consent, and checksum verification.
- Never modify or overwrite previously published tags, releases or binary assets.
- Never access the owner's actual network devices, desktop or files. Use fixtures and hosted CI.
- Redesign, consolidate and rename controls when owner-approved; preserve actions and data.
- Native minimum dimensions in Phase 2: main 960×600, detached Editor/Terminal 640×400.
- The old 390px Editor comparison-motion drift test and its 2px threshold are retired. Narrower widths are unsupported; use behavior/data tests and screenshot review instead of pixel-specific cosmetic gates.
- No application-code changes in Phase 1. After the UX audit, **stop for explicit approval** before implementation.
- Work in 1.18.x betas, one per approved implementation phase (2 through 6).
- Update checks must eventually run at startup and every six hours, with manual checking and explicit user approval to download/install retained.
- Keep What's New short, plain-language and focused on the experience; technical detail belongs under Additional Details. The updater shows every What's New item in full (owner request, v1.21.5), so keep the list to a few clear sentences.

## Repository layout
- cmd/network-toolkit/: Go application and Windows native host; internal/: platform, network operations, security, Terminal and transfer logic.
- web/: UI sources; assets/ and themes/: resources; scripts/: tests, generators and release tooling.
- docs/guide/: user-facing topic guides; docs/releases/: archived release notes; docs/archive/: superseded plans; docs/RELEASE###_HANDOFF.md: historic engineering handoffs.
- Keep root documentation concise, with at most one latest-beta reference in README.
- CLAUDE.md sits in the root (allowlisted in scripts/repository_layout_test.py) because Claude reads it there; it only imports this file and docs/REPOSITORY_STANDARDS.md.
- README images live in docs/images/ (hero.png plus kebab-case names) and are regenerated with `node scripts/readme-screenshots.browser.cjs` (synthetic data only; see its header for the packet capture shot).
- Preserve the portable executable filename Network_Toolkit.exe and the existing update feed semantics.
- Dropdowns (v1.21.10): `web/assets/dropdowns.js` converts every `<input list="…">` into an app-styled combobox and removes its `list` attribute (kept as `data-combobox-list`), so never rely on `input.list`. Selects stay native while closed and switch to the app-colored list (`.ntk-picker`, base-select) only while open; do not style closed selects with `appearance: base-select`, because it changes their size and CI compares layouts with pinned older builds.
- Terminal settings has tabs: Appearance (with highlighting since v1.21.19), Features, Mouse & keyboard. The Syntax highlighting picker and the preview are pinned together (`.terminal-preview-sticky`, built in `mount()` of terminal-appearance.js); settings that change how output looks go below it so the preview shows their effect. Put a new terminal option in the matching tab (`[data-terminal-settings-panel="…"]`, or mark markup in `terminalToolsHTML()` with `data-terminal-settings-target`); never add app-level buttons (theme, app settings) to it. The Tools menu is gone (v1.21.18): `#terminalToolsPanel` is only a hidden staging container that terminal-extras.js empties into the active-session bar and the Settings tabs. Connection tools belong in the Saved sidebar (footer: Password manager, SSH host keys), not in a new toolbar menu. Separate terminal windows show theme, window settings and help at the bottom of the terminal sidebar rail (`terminalAppToolsHTML()`), not in the toolbar: the toolbar must stay one row in a 1024 px terminal window, because app-chrome109 compares that window's terminal height with 1.17.108 and CI's fonts are wider than local ones.
- Universal highlighting (v1.21.12): its rule switches and colors live on the Customize dialog's Universal page (`universalEditorHTML()`, `[data-terminal-universal-editor]` is in `SECTIONS` of terminal-appearance.js, so the same change/sync handlers serve it). `highlightOptions()` without a language returns the active rule set; pass `ruleset:null, ruleSet:null` to `legend()` when you need Universal's own colors.
- Terminal links (`ssh://`, `telnet://`, `serial:`): `cmd/network-toolkit/terminal_link.go` is the only parser and `--terminal --open-url "<link>"` the only command (no other switch is accepted with it, so a quoted link cannot add arguments). A link only prefills the connection form (`web/assets/terminal-links.js`): never auto-connect, never take a password from a link, never pick a credential, host key or profile without the user. Setup (`scripts/installer/windows.nsi`) registers per user via Capabilities\URLAssociations, never writes a UserChoice, and creates a scheme key only when neither HKCU nor HKLM has one (recorded under `Software\Network Toolkit\Terminal\CreatedSchemes` so uninstall removes only those). Links stay in the in-memory request inbox: never save them in settings, and keep `--open-url` out of `updateRestartArgs`. The Linux edition has no standalone Terminal menu entry, so it registers no link handler.
- Shared app data (docs/SHARED_APP_DATA.md): the main window (portable or installed), the standalone Terminal and the standalone Text Editor share one set of settings and saved data per data folder. `sharedDataKeys` in cmd/network-toolkit/shared_data.go is the one table of shared keys and `perWindowStateKeys` the list of per-window ones; classify every new state key in one of them (shared if the user sets it on purpose, per-window if it is about one window or one run; `TestSharedKeyTableClassifiesEveryPageKey` and the shared-data browser check fail otherwise) and mirror a shared key in `LIVE`/`AT_START` of web/assets/shared-data.js. A page sends, in `_sharedBase`, the earlier value of each shared key it changed; the engine merges three ways (page, that earlier value, disk: lists by id, objects by member, a change beats a removal, the page's edit wins a conflict) under the data folder's lock and leaves unlisted shared keys as they are on disk. **Never shorten a saved list** (saved sessions, FTP connections, targets, TFTP profiles: `MaxSaved` in the table, `SAVED_LIMITS` in shared-data.js): a shorter list reads as removals for every app, so load and save it whole, and when it is full refuse the new entry with `NetworkToolkitSharedData.full()`; scripts/shared-list-limits.test.cjs fails on a `.slice(0,n)` of such a list. Read the data folder's settings file only with `readSharedSettings` and write it only with `writeSharedSettings` (or `updateSharedLocked` from engine code): they keep the mark and the copy of the saved lists (`Network_Toolkit.saved-lists.json`) that put entries back after a version from before sharing, which does not merge, saved over them. A writer that may meet a missing settings file calls `recreateRootLocked` first (it writes what the app holds plus, from the copy, what it does not hold; a standalone app without a usable copy still writes and notes `sharedMainOnlyAbsent`, so a main window keeps its own keys) and `wroteSharedLocked` after; `TestSharedSettingsWritersAreKnown` lists the writers. `writeSharedSettings` returns the file as written (the mark carries the file's id), so keep that, not what was passed in. The copy is paired with its settings file by that id, kept a third time in `Network_Toolkit.Views/000…0/Network_Toolkit.window.json`, which every version's "Delete app data" removes: never use a copy except through `usableSavedListsCopy`/`readSharedSettings`, or an older version's deletion is undone. Anything taken from the copy is named in a `recovered` notice. For every file of shared data, "does not exist", "could not be read" and "read and different" are three answers: ignore, replace or remove something only on a confirmed answer, and on a read error change nothing and report "try again" (`errSavedListsUnread`; tests make one read fail with `readCredentialFault`). A read that fails is never "the file was reset" (settings, vault, host trust); files several apps read and replace are opened and replaced through internal/sharedfile. Standalone workspace folders hold only window state (plus the untouched pre-sharing copy, which newer versions never use); credentials, SSH host trust and macros are the data folder's files. "Reopen files next time" is shared, so kept unsaved text must never stay hidden or be removed unseen: an editor reopens it even with the setting off, and the engine refuses a session save or delete from a run that was not given the session (editor_session.go). The one-time migration records its work in `Network_Toolkit.shared-data.json` and keeps `Network_Toolkit.before-sharing.*` copies; it only adds, never overwrites. Moving and deleting app data cover all three workspaces (`storageWorkspaces`); add any new shared file to `storagePortableFiles`.
- Window launch and peer send are two separate uses of a window's activation token (`terminal_window.go`, `peer_send.go`). **Launch** requests (a second start, a link, a file from Explorer) still carry only connection settings or a file to open: never authentication, never terminal input. **Peer send** carries text only, only between the standalone Text Editor and the standalone Terminal of one data root, found through the other app's instance record. That record is protected (DPAPI on Windows for main, editor and Terminal; a private 0600 file elsewhere): never write a plain record, and never trust a plain record for peer send (an older Terminal's plain record may still receive launches). `/api/peer/` accepts the activation token only, from loopback only, never from a page, with strict JSON and size limits (1 MiB to a terminal, 8 MiB to the editor), one pending request for at most a minute. The receiving page must use the same code as a send inside one window: `pasteText` for the Terminal (paste review, paste warnings, bracketed paste), `newDocument`/`insertText`/`pickInsert` for the editor, and it must never replace an open dialog. Never add credentials, tokens, host keys, file paths, automatic Enter or command execution to either path, and never show the other app's token to a page.
- Standalone apps (`--editor-standalone`, `--terminal`; `web/assets/standalone-apps.js`, checked by `scripts/standalone-apps.browser.cjs`): nothing visible that does nothing, and nothing from another tool unless it connects to the other standalone app (Send to terminal, Send to Text Editor). Hide what can never work there instead of showing it disabled. A new palette command, help row, settings section or cross-tool button needs a decision for each standalone app. Local Windows shells are part of the standalone Terminal: Command Prompt and PowerShell on the Start a terminal card, in the connection form, in saved and recent connections, with starting folder and Run as administrator, must behave exactly as in the main window (that card is built once, so anything on it that depends on `/api/status` must be refreshed by `refreshTerminalWelcome()`). The main window and detached child windows must not change.
- New saved UI settings must survive a restart: `mergeState` in web/index.html (or the module's `mergePreferences`) has to restore the key, and keys with a Go sanitizer (`transferClientLayout`, `transferServerSidebar` in transfer_client_settings.go) must allow the new field. The Text Editor sidebar preferences were silently dropped until v1.21.3 for this reason.
- Text Editor session restore (`restoreSession` in `editorPreferences`, default on): only the primary workspaces (main window, standalone Text Editor) keep a session, in `Network_Toolkit.editor-session/` beside their settings (editor_session.go, editor-session.js); detached editor windows never save or restore one, and the renderer uses it only when `/api/status` reports `editorSessionAvailable`. The index holds metadata only, never text, bindings or credentials. Kept copies of disk-backed documents are streamed by Go from a buffer snapshot (`source:'buffer'`), never sent through the renderer, and have no size ceiling. App/window close keeps the session before prompting and asks only about documents that could not be kept; tab close and Close editor prompt as before. Storage moves stream the session (storage_editor_session.go); deleting app data removes it.

## Build and test
Use the repo's existing scripts and vendored dependencies:
- Icon manifest checks require the exact committed SVG bytes. Windows checkout line-ending conversion can change their checksums; preserve LF for `assets/Network_Toolkit_Icon.svg` and `assets/source/Network_Toolkit_Icon.original.svg` instead of regenerating the published icon.
- go test -mod=vendor ./...
- To check that the app compiles, use go build -mod=vendor -o /dev/null ./cmd/network-toolkit (or go vet). A bare go build ./cmd/... writes a 25 MB ./network-toolkit binary at the root; it is in .gitignore and must never be committed (it once slipped into a PR via git add -A). Browser tests run locally write screenshots and reports to ./test-results/ (also ignored); stage files by name instead of git add -A.
- node --test scripts/*.test.cjs
- python3 -m unittest discover -s scripts -p '*_test.py'
- python3 scripts/github_release.py validate
- python3 scripts/build_windows_resources.py
- sh ./build.sh

Native Explorer drag tests must not release the mouse after a fixed delay. The page arms the native copy only when the pointer leaves the source window, which on the hosted 1024px screen happens on the last travel steps. `native-terminal-sftp123.ps1` therefore releases only after the native drag trace reports Explorer's COPY feedback (`Wait-NativeDropAccepted`; the child is built with `toolkit_native_drag_trace122`). If a native drag ends with outcome `cancelled` and no `materialize`, the release came before OLE admission. It does not mean Explorer copied slowly.

Browser tests that list or compare a form's controls must wait until the form has stopped changing: `input-clear.js` (Clear buttons) and `dropdowns.js` (Show all choices) add their buttons on the animation frame after the form appears, so a list read at once may or may not include them (`connectForm()` in `scripts/standalone-apps.browser.cjs` shows the wait).

Setup uninstall checks (`scripts/installer/verify-windows.ps1`): an NSIS uninstaller copies itself to a temporary folder, starts that copy and exits at once. Run it with `Invoke-Uninstaller` (only the in-place `_?=` run uses `Invoke-Silent`) and keep its order: read the launcher's exit state first, then list its child processes (the other order can report "finished" while the copy still works). `Assert-UninstallFinished` names the cause when the program file is still there (refused, copy still running, open program, or a delete Windows completes later); it fails in every case, so do not turn its wait into a pass. Silent Setup and Uninstall show no message: every refusal goes through `StopSetup` in `scripts/installer/windows.nsi`, and a failed install names its step in `$FailedStep`, both written to `%TEMP%\Network_Toolkit_Setup.log` (message only, never a path or name; removed at the start of each run). `Invoke-Silent` prints that reason on an unexpected exit code and checks it on expected refusals, so give a new refusal a `StopSetup` text and a new install step a `$FailedStep` name. Staged files are moved into place with `PlaceStagedFile`, which retries sharing and access errors for about five seconds.

Where fixtures/browser/native host tests need platform-specific setup, run the established .github/workflows/checks.yml jobs in hosted GitHub Actions. Checks runs twice for a pull request from a branch in this repository (push and pull_request events); merge only when both runs are green, re-running a failed job rather than relying on the other run. Never claim physical Windows or live-device acceptance from synthetic tests.

## Linux edition
- Plan and phase status: docs/LINUX_PLAN.md. Windows file names, the Windows updater, saved data and behaviour must not change for Linux work.
- In Linux window mode the session token reaches only the window the app opened (one-time `/launch` link and `ntk_window` cookie, `browser_launch_gate.go`). Never serve the token in a page without that check, and never launch a browser with `--no-sandbox` or similar.
- Releases include `Network_Toolkit_<ver>_Linux_x86_64.tar.gz` and `_Linux_aarch64.tar.gz`; `build.sh` builds them and `github_release.py package` needs `--linux-x86-64` and `--linux-aarch64`.
- `build.sh` pins `GOTOOLCHAIN=local`; if the system Go is older than go.mod, put the matching toolchain first on PATH.

## Release procedure
1. Inspect the current main branch, release notes, handoff, tags, CI and updater channel.
2. Make one reviewed beta per approved UX phase, with relevant behavior/data regressions and screenshots.
3. Record status and known limitations in concise handoff; keep technical CI evidence in an appendix.
4. Run release guards and required CI, never silence genuine security/data failures.
5. Publish via the existing guarded .github/workflows/release.yml process only after the phase is approved.
6. Verify source/tag, the executable, portable and updater ZIPs, SHA256SUMS, update-feed selection and stable-channel isolation.
7. Never replace a published release or change saved state and authorization boundaries.

## Owner approval gate
Phase 0: docs only, no release. Phase 1: audit all tools at 1280×800 and 1920×1080 in light/dark, document consolidations/settings/confirmations/discoverability, and **stop**. Implement Phases 2 to 6 only after owner approval; after Phase 6 establish docs/UI_GUIDELINES.md and freeze layout pending owner approval for later moves.

## Repository standards (all contributors and AI tools)

This repository follows the shared TechSavage1989 standard in [`docs/REPOSITORY_STANDARDS.md`](docs/REPOSITORY_STANDARDS.md), the same file in every app repository. Read it before changing anything. In short:

- **README:** centered header (real icon, one `<h1>`, tagline, quick links Download · Get started · Features · Screenshots · Updates · Development, hero image), then the standard section order. Update it in the same pull request as any user-visible change.
- **Screenshots:** real captures with fictional data in `docs/images/` (`hero.png` + kebab-case names). Recapture any screenshot a UI change makes stale, in the same pull request.
- **Layout:** compact root; respect the root allowlist and checks above. Never commit build output, binaries, archives, logs, caches or secrets.
- **Branches:** short-lived `feat/` `fix/` `docs/` `chore/` `release/` branches, one focused change per pull request, merge only on green checks, delete the branch after merging. AI sessions cannot delete branches through their GitHub access, so `.github/workflows/delete-merged-branches.yml` does it after every push to main: it deletes branches whose pull request was merged (tip unchanged) or that main already contains and are over a day old, never the default, protected or open-PR branches, and lists kept branches with unique commits in its run summary. To remove unmerged branches the owner has approved, start it from this session with `gh api -X POST repos/TechSavage1989/network-toolkit/actions/workflows/delete-merged-branches.yml/dispatches -f ref=main -f 'inputs[branches]=<names>'` (default, protected and open-PR branches are refused; each deleted branch's last commit is logged for restore). Don't ask the owner to delete branches by hand.
- **Instructions:** this file is the single source of project rules for every tool; `CLAUDE.md` imports it. Add new rules and gotchas here.

Where this file's project-specific rules differ from the shared standard, this file wins; an enforced check script wins over both.
