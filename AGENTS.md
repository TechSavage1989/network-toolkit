# Network Toolkit standing instructions

## Authority and scope
Read [docs/UX_POLISH_PLAN.md](docs/UX_POLISH_PLAN.md) first. It is the owner's authoritative UX plan; follow [docs/DEVELOPMENT_ROADMAP.md](docs/DEVELOPMENT_ROADMAP.md) for phase status. Historical plans in docs/archive/ are not active requirements. Read docs/DEVELOPMENT_HANDOFF.md for current progress.

**Never prepend release records to AGENTS.md or README.md.** Keep release history in CHANGELOG.md and per-release technical evidence in docs/releases/ or existing docs/RELEASE###_HANDOFF.md files.

## Working with the owner
- The owner has given standing approval to publish new betas when their required release checks pass. Proceed through publication and verification without asking for release confirmation again.
- When the owner's input or decision is needed, when a release has been published, or when work is waiting on the owner, start that message with a bold, clearly marked line (for example **⚠️ ACTION NEEDED:**, **✅ PUBLISHED:** or **⏳ WAITING ON YOU:**) so it cannot be missed (owner request, 2026-11-07).
- End every message to the owner with a clear status: what is done or published, what is running and roughly when it finishes, and what (if anything) the owner needs to do (owner request, 2026-11-07).
- Terminal settings modeled on MobaXterm are planned in [docs/TERMINAL_SETTINGS_PLAN.md](docs/TERMINAL_SETTINGS_PLAN.md).

## Owner's non-negotiables
- Text Editor scalability (owner clarification, 2026-11-08): work effectively with text files of any size while keeping interaction and the rest of the app responsive. Fixed 16/32 MiB file and 30,000-line limits do not meet this requirement. Follow `docs/EDITOR_SCALABILITY_PLAN.md`; do not publish the current bounded-file candidate as completing it.
- Never lose credentials, vault entries, saved profiles, preferences, macros, unsaved work or active sessions. Migrate settings explicitly.
- Preserve Windows/UAC authorization, Hosts/IP/adapter review, explicit download and install consent, and checksum verification. One owner-approved exception (2026-11-11): the start that follows an update the user approved adds that same version's separate Text Editor and Terminal programs without another question (see Separate programs below).
- Never modify or overwrite previously published tags, releases or binary assets.
- Never access the owner's actual network devices, desktop or files. Use fixtures and hosted CI.
- Redesign, consolidate and rename controls when owner-approved; preserve actions and data.
- Native minimum dimensions in Phase 2: main 960×600, detached Editor/Terminal 640×400.
- The old 390px Editor comparison-motion drift test and its 2px threshold are retired. Narrower widths are unsupported; use behavior/data tests and screenshot review instead of pixel-specific cosmetic gates.
- No application-code changes in Phase 1. After the UX audit, **stop for explicit approval** before implementation.
- Work in 1.18.x betas, one per approved implementation phase (2 through 6).
- Update checks must eventually run at startup and every six hours, with manual checking and explicit user approval to download/install retained.
- Keep What's New short, plain-language and focused on the experience; technical detail belongs under Additional Details. The updater shows every What's New item in full (owner request, v1.21.5), so keep the list to a few clear sentences.

Only a file's icon uses 3: the ProgID's `DefaultIcon`, rewritten by every install and upgrade (1.21.44 and earlier wrote 1), by the portable registration, and by the first start after an in-app update (`editorRegRepairDocumentIcon`: only that value, only when the ProgID's `shell\open\command` starts the running `Network_Toolkit.exe`, then `SHChangeNotify`; never a ProgID of another program). Released Setups and shortcuts name 0 to 2, so never reorder or remove a group: append new ones (`scripts/windows_resources_test.py` checks this). The document icon is the editor icon's sheet without its tile (`assets/source/Network_Toolkit_Document.svg`, with pixel-grid drawings `Network_Toolkit_Document.<16|20|24|32>.svg` for the small sizes); regenerate it with `python3 scripts/generate_icon_assets.py --document` (Inkscape), which never touches the published icons, then `python3 scripts/build_windows_resources.py`. - Portable Text Editor registration ("Use this copy's Text Editor in Windows", App settings → Editor of the Windows main window; `cmd/network-toolkit/text_editor_registration.go`, page `web/assets/windows-integration.js`): every rule of the bullet above applies. On the user's click only (never at startup; the startup check only reads and offers **Clean up** for a registration whose program is missing), the portable copy writes Setup's keys and values for itself, with `editorRegCommand(exe)` (`${EDITOR_COMMAND}`'s shape), the editor icon for the application values and the document icon for the ProgID, for the types in `textEditorExtensions`, which `node scripts/text-extensions.cjs --write` generates from text-extensions.nsh (`scripts/text-extensions.test.cjs` and `TestEditorRegistrationMatchesSetup` fail when Go and Setup differ). Its record is `Software\Network Toolkit\PortableTextEditor` (`Executable`, `ContextMenu`, `CreatedKeys` named like Setup's), written before the keys; a key is recorded only when this registration created it, and Remove deletes values it wrote and then keys only through `editorRegDeleteEmpty` (the Go port of `DeleteEmptyUserKey`; `DeleteKey` never deletes a tree). Plans are computed from reads through the `editorRegistry` interface (tests use an in-memory registry), a read error writes nothing, and each action holds Setup's mutex `Local\NetworkToolkitSetup` and ends with `SHChangeNotify(SHCNE_ASSOCCHANGED)`. Ownership: **the installed program wins** — while the uninstall key names an `InstallLocation`, a portable copy refuses register, takeover and remove and says so. **Setup takes a portable registration over**: `AdoptPortableRegistration` copies the portable `CreatedKeys` into Setup's before the types are registered, `RegisterApplication` rewrites an `Applications\Network_Toolkit.exe` entry that starts the recorded portable program, `.onInit` preselects the right-click box when the portable record has `ContextMenu` (cleared, Setup removes the entry), and `RetirePortableRegistration` deletes the portable record after Setup's registration is written; uninstall then removes everything as Setup's own (a rolled back install leaves the portable record, whose copy then reports an incomplete registration to repair). **One portable copy at a time**: another copy (or an unrecorded registration) is replaced only with `takeover` after the user confirms; the record and its `CreatedKeys` carry over. The program file must be named `Network_Toolkit.exe`. Register and takeover are refused (`errEditorRegPercent`, `errEditorRegUnsafe`, through `editorRegStatus`) when the program path holds a `%` (Explorer expands `%1`/`%L` inside the program path too; Setup's `ValidateInstallDirectory` refuses such a folder through `StopSetup`) or when anyone but this user, SYSTEM, Administrators or TrustedInstaller can change the program or its folder (`editorRegWritableByOthers` reads the owner and DACL; every double-clicked text file would run that copy). Remove is for this copy's own registration only; another copy's registration is cleaned up only through `/text-editor/cleanup` with the `owner` the page showed, refused (`errEditorRegStale`) unless the registration still names it and that program is confirmed missing. A program whose drive or share is not connected (or could not be checked) is `ownerUnreachable`, never missing (`editorRegClassify`), and offers no clean up. The hidden switch `--text-editor-registration=register|register-menu|takeover|takeover-menu|remove|cleanup` (alone only; exit 0 done, 2 failed, 3 installed program, 4 another copy, 5 file name, 6 nothing of this copy's or nothing to clean up, 7 location refused) exists for the hosted check, which runs portable register/remove (all of `HKCU\Software\Classes` but `Local Settings` compared), two copies with takeover and cleanup, portable then Setup, and Setup then portable.

Never offer an older release: it could save over settings a newer version wrote, and its Setup would not take over the portable registration; otherwise say that no installer was found for this version (`errFullInstallNoNewer`). Network access only through `updateFetch`/`updateFetchProgress`/`updateHTTPClient` (the updater's hosts and redirect rule) while holding the updater's `networkBusy` slot; verification only through `updateVerifySum` against that release's SHA256SUMS, in memory, before anything is written; a mismatch writes nothing. Starting needs `{version, confirm:true}` after the download's own `{version, confirm:true}`: the page asks twice (`data-windows-install-confirm`). Downloads never live in the data folder (the user may have put it where others can write): `%LOCALAPPDATA%\NetworkToolkit-Setup\.network-toolkit-setup-<random>\`, both levels created with a protected owner-only DACL at creation (`fullInstallMakePrivateDir`) and accepted only as plain folders nobody else can change (`fullInstallCheckPrivateDir`: no junction or link, `editorRegWritableByOthers` empty). `fullInstallLaunchVerified` repeats those checks, opens Setup once with `FILE_SHARE_READ` only and no reparse following, checks that the handle's final path is the expected one, hashes it from that handle and starts it with `CreateProcess` (no arguments: interactive, never `/S`) while the handle is still open; any failed check refuses to start, and changed bytes delete the download. The start does not hold `fullInstall.mu` (a `starting` flag refuses a second start). Downloads are removed by discard, at exit when never started, and by the next download. `full_install_windows_test.go` proves the owner-only folder, the refused junction and that the held file cannot be written, renamed or deleted while the started program is the verified file. The installed program is found through the uninstall key; "Open the installed program" starts it, "Reinstall or repair anyway" still offers Setup. The data folder note comes from `storage_location.go`: only an explicit `--data-dir` run uses a folder the installed program does not read. The routes `/api/windows-integration/…` exist in the main window only.
- Text Editor opens any file (`Import` in internal/editorbuffer/codec.go, used for local, remote, dropped and kept files): an untouched save writes the bytes that were read, and an edited save changes only what was edited. UTF-8 and BOM-marked UTF-16 as before; text that is not valid UTF-8 is `Windows-1252` (all 256 bytes are distinct characters; a character it lacks stops the save with `ErrUnencodable`, never a replacement); lines that end in different ways give the `Mixed` line ending (internal/editorbuffer/eol.go): the buffer records each line's ending by scratch-file offset (`eolMap`, immutable, one per snapshot), so unedited lines keep theirs and typed lines get the most common one. **What is written must reopen as the text the editor showed**: a bare LF directly after a lone CR would read back as one CRLF, so `encode` writes that LF as CRLF, the one case in which an untouched ending changes its bytes (`mixedModel` in mixed_reopen_test.go is the specification, checked for Encode, export and the kept copy). **A command must not replace more text than it changes** in such a document: every '\n' in new text is a new line break. `Buffer.Edit` therefore leaves out what the new text repeats at both ends of the range, an edit or bulk edit that replaces lines by as many lines keeps each line's ending (`inherit`), and Replace All is `Snapshot.ReplaceAll` (per match, one undo step), never a rewrite of the document. A `Snapshot` holds the buffer open (the `lifetime` read lock): release it before calling anything that claims that lock again (`Edit`, `History`, `BeginEdit` and the transaction methods), because a `Close` waiting in between makes the second claim wait forever, with the document's edit lock held; `Replacement.Commit` and `Abort` take only the editing mutex for that reason, every caller of `ReplaceAll` defers `Abort` (it returns the new text's space unless committed), and whoever replaces or closes a document's buffer calls `stopReplaceAll` first. Tests of anything that could wait on a lock use a time limit (`within`, `finishes`); `TestEditorRangeCommandsKeepMixedLineEndings` lists the page's commands, so add a row for a new one. **A file that is not text** (NUL bytes, invalid BOM-marked UTF-16) is `Imported.Binary` with encoding `Binary`: its buffer is a display rendering only, and `Buffer.Edit`, `BeginEdit`, `History`, `Encode`, `PrepareEncoding`, `WriteKept`, `ReplaceAll`, the session snapshot and every engine action except status, window, find, reload and reading it again from a browser file refuse it (`ErrBinary`, in the engine, not only in a handler; `TestBinaryBufferRefusesEveryWrite` walks them); never add a path that writes it. These three formats exist only in disk-backed documents: `engineFormat()` in file-editor.js keeps such a document from becoming a page-held one, `validateEditorBatch` refuses them for page-held text, and a kept copy of unsaved work is written with `Snapshot.WriteKept` so mixed endings survive a restart. A source that cannot be read twice (not an `io.Seeker`) keeps the strict reading.
- Shared app data (docs/SHARED_APP_DATA.md): the main window (portable or installed), the standalone Terminal and the standalone Text Editor share one set of settings and saved data per data folder. `sharedDataKeys` in cmd/network-toolkit/shared_data.go is the one table of shared keys and `perWindowStateKeys` the list of per-window ones; classify every new state key in one of them (shared if the user sets it on purpose, per-window if it is about one window or one run; `TestSharedKeyTableClassifiesEveryPageKey` and the shared-data browser check fail otherwise) and mirror a shared key in `LIVE`/`AT_START` of web/assets/shared-data.js. A page sends, in `_sharedBase`, the earlier value of each shared key it changed; the engine merges three ways (page, that earlier value, disk: lists by id, objects by member, a change beats a removal, the page's edit wins a conflict) under the data folder's lock and leaves unlisted shared keys as they are on disk. **Never shorten a saved list** (saved sessions, FTP connections, targets, TFTP profiles: `MaxSaved` in the table, `SAVED_LIMITS` in shared-data.js): a shorter list reads as removals for every app, so load and save it whole, and when it is full refuse the new entry with `NetworkToolkitSharedData.full()`; scripts/shared-list-limits.test.cjs fails on a `.slice(0,n)` of such a list. Read the data folder's settings file only with `readSharedSettings` and write it only with `writeSharedSettings` (or `updateSharedLocked` from engine code): they keep the mark and the copy of the saved lists (`Network_Toolkit.saved-lists.json`) that put entries back after a version from before sharing, which does not merge, saved over them. A writer that may meet a missing settings file calls `recreateRootLocked` first (it writes what the app holds plus, from the copy, what it does not hold; a standalone app without a usable copy still writes and notes `sharedMainOnlyAbsent`, so a main window keeps its own keys) and `wroteSharedLocked` after; `TestSharedSettingsWritersAreKnown` lists the writers. `writeSharedSettings` returns the file as written (the mark carries the file's id), so keep that, not what was passed in. The copy is paired with its settings file by that id, kept a third time in `Network_Toolkit.Views/000…0/Network_Toolkit.window.json`, which every version's "Delete app data" removes: never use a copy except through `usableSavedListsCopy`/`readSharedSettings`, or an older version's deletion is undone. Anything taken from the copy is named in a `recovered` notice. For every file of shared data, "does not exist", "could not be read" and "read and different" are three answers: ignore, replace or remove something only on a confirmed answer (tests make one read fail with `readCredentialFault`, the settings write with `writeRootSettingsFault`). The settings file is the user's data and the copy and its id file are protection: a problem with the protection never refuses a save or a move. Save the settings, leave a copy or id file that could not be read untouched, note `sharedCopyBehind` in the settings file so the put-back happens when the copy is readable, and tell the user which file it is (`protectionProblem`). Refuse a save only when the settings file itself could not be read or written or the lock is busy; the page retries a refused save (`retrySave`, `saveBeforeClose` in web/index.html), and what an app holds beyond the file (`heldExtra`) is retried with a backoff and never given up. A read that fails is never "the file was reset" (settings, vault, host trust); files several apps read and replace are opened and replaced through internal/sharedfile. Standalone workspace folders hold only window state (plus the untouched pre-sharing copy, which newer versions never use); credentials, SSH host trust and macros are the data folder's files. "Reopen files next time" is shared, so kept unsaved text must never stay hidden or be removed unseen: an editor reopens it even with the setting off, and the engine refuses a session save or delete from a run that was not given the session (editor_session.go). The one-time migration records its work in `Network_Toolkit.shared-data.json` and keeps `Network_Toolkit.before-sharing.*` copies; it only adds, never overwrites. Moving and deleting app data cover all three workspaces (`storageWorkspaces`); add any new shared file to `storagePortableFiles`.
- Window launch and peer send are two separate uses of a window's activation token (`terminal_window.go`, `peer_send.go`). **Launch** requests (a second start, a link, a file from Explorer) still carry only connection settings or a file to open: never authentication, never terminal input. **Peer send** carries text only, sent only by the standalone Text Editor or the standalone Terminal of one data root, found through the receiver's instance record. The sender's engine picks the receiver in this order and never asks the user to open anything (owner request): the other standalone app if it runs; otherwise the main Toolkit window of the same data root while its page runs (its Terminal page or its Text Editor; `status.peerReceive` starts that page's inbox; a main window whose protected record is valid and whose engine answers but whose page has not polled within `peerTargetsFresh` is probed again for up to `peerMainGrace` (3 s, `peerProbeMain`, bounded by the sender's request) before it is passed over, so a send just after it opened does not start the other app; only the main window gets this, a standalone app counts as running while it starts); otherwise it starts the other standalone app with the existing fixed launch arguments (`launchPeerApp`; never text on a command line) and holds the text in its own memory until that app's record appears and its page is ready, for at most `peerLaunchWait` (25 s, under the server's 30 s write timeout), then delivers it once. A send still waiting when the sender closes is dropped, never saved; on a timeout the user is told and their text stays where it was. Terminal text needs a session the user connected: with none, say so as a send inside one window does, and never connect one. A page shows targets from one receiver and the engine itself sends a session or an open document only to that receiver (`peer.listed`): with nothing listed such a send is refused ("Choose Send to … again"), never routed to whichever app runs. Text goes only to the instance that was just probed: `peerDeliver`/`peerCall` take that instance id and compare it with the record before anything is sent. "Is another send starting?" and recording the new send happen under one lock, so two sends never both start the other app. `launchPeerApp` gives foreground rights only to a process named by a record peer send trusts (`peerForegroundPID`), never from a plain record. The main window only receives text: its own Send to commands never use peer send (they stay inside its engine, below), it sends no text or sessions anywhere, and child windows have no peer routes at all. Its one sending use is the **document hand-over** (owner decision, `peer_handover.go`, `web/assets/editor-handover.js`): when the user moves main-window editor tabs to a **new** window with Detach editor or Move all (`move(..., {handover:true})`; owner decision: Move to separate window on a single tab always gets its own connected window, and never a tab drag or a child window) while the standalone Text Editor of the same data root runs and its page is ready, local and untitled tabs go to that editor instead; everything else (SFTP/SSH bindings, `Binary`, disk-backed tabs with unsaved changes, formats other than UTF-8/UTF-16 with LF/CRLF/CR, files not on disk yet or changed on disk) goes to a connected window as before, and with no such editor nothing changes. Routes: the main page's `/api/peer-handover/` (`receiver`, `start`, `result`; session token, main window only) and the editor's `/api/peer/documents/` (`status`, `handover`, `result`; same guards as text, kind `documents`, 12 tabs and 8 MiB of text per request, the one pending request shared with text), always pinned to the probed instance (`peerCallReceiver`). **Never lose a tab**: the page freezes the tabs (`snapshot`), and only tabs the editor's page confirmed per tab (`ack` with `items` naming every sent tab once) are released; a refusal, an expiry, a lost receiver or an invalid confirmation gives every tab back (`rollback`), so at worst both windows hold a tab, never neither. The receiving page opens a file only through the ordinary local open (`adoptHandover` in file-editor.js), applies unsaved text only when the file still has the read digest and the format matches, removes what it could not carry exactly (`discardAdopted`, only an untouched tab it created), and with "Reopen files next time" on confirms unsaved text only after `session.save()` kept it. **File paths** travel on this route only (owner-approved exception): absolute local paths (a drive letter on Windows, `/` elsewhere; no UNC, device, network-drive, `.`/`..` or stream path; `peerHandoverLocalPath`), checked by both engines, with a dirty file's digest checked by both (`peerHandoverUnchanged`). Undo history is not handed over. Terminal sessions never move to the standalone Terminal. A running app with a plain or unreadable record, or without `/api/peer/` (an older version), is never a receiver: skip it and name it to the user (`peerNote`). That record is protected (DPAPI on Windows for main, editor and Terminal; a private 0600 file elsewhere): never write a plain record, and never trust a plain record for peer send (an older Terminal's plain record may still receive launches). `/api/peer/` (the same routes and guards in the standalone apps and in the main window, which serves both kinds) accepts the activation token only, from loopback only, never from a page, with strict JSON and size limits (1 MiB to a terminal, 8 MiB to the editor), one pending request per window for at most a minute. The receiving page must use the same code as a send inside one window: `pasteText` for the Terminal (paste review, paste warnings, bracketed paste), `newDocument`/`insertText`/`pickInsert` for the editor, and it must never replace an open dialog: `blocked()` in peer-send.js (app dialogs, a native `dialog[open]` such as the colour picker, the editor's Move / merge box, and in the main window a password being typed) is asked before the window changes page and again, as `guard`, immediately before `pasteText`, `newDocument`/`insertText` and `pickInsert`. The sending page follows the same rule: after the automatic open (up to 25 s) `openPeer` shows a message instead of a dialog if another dialog is open by then. Known limit: a main window that registered its record polls its own engine's peer inbox once a second while it is open. Never add credentials, tokens, host keys, file paths (beyond the hand-over's local paths), automatic Enter or command execution to either path, and never show the other app's token to a page.
- Hand-over receiving (`adoptHandover` in file-editor.js): it returns `{document, created}`; a file already open (matched by the engine's `canonical-path` key: links resolved, long names, case-insensitive on Windows, never a JS guess) returns the existing tab with `created:false`, and only tabs a request created are counted as unsaved or discarded by it. A start whose reply is lost says the tabs stay here and to check the Text Editor; a result check that fails is retried until `peerHandoverStatusDeadline`. Known limit: the network-drive refusal (`peerHandoverRemoteDrive`) checks the drive letter only, so a junction on a local drive that points to a share passes it; the main window already read the file through that path, so nothing new is exposed.
- Window send (`window_send.go`, `web/assets/window-send.js`; main Toolkit engine only, `windowSendAvailable`): Send to terminal and Send to Text Editor reach the other windows of one engine (main window, detached Terminal windows, detached editor windows). It is not peer send and never leaves the engine. Each window's page polls `/api/window-send/inbox` under its own token and reports only targets it shows (the engine drops sessions it does not own); the engine sends to a window only while it is alive, freshly polled, lists the target, still owns the session (`ownerLocked`, as `withTerminalOwner`) or holds the document without a pending move, with one waiting request per window. The receiver uses peer-send.js `receiveTerminal`/`receiveEditor` (the in-window paste and insert paths) behind `blocked()`; text only, no Enter. A new send path or target kind needs the same checks and a row in `TestWindowSendRefusesWhatTheWindowDoesNotHold`; `TestWindowSendBrowser` drives the real pages. Kind `remote` (owner decision): **Edit** in the SFTP browser of a detached Terminal **workspace** asks the main window to open that file; the engine checks the workspace owns the session and records a grant for that one path on that SSH transport, and the main page opens it with its SFTP browser's own Edit code. The grant is tied to the asking workspace view, its request and the main window's tab: a refused or expired request, or the tab disappearing from the main page's report (closed, or moved away), drops it (`dropGrantLocked`). It admits only read-text and write-text of that path from the main window (`remoteBrowserGrant`) and the editor's disk buffer for it (`makeGrant`, `fixedPath`), every operation through `windowSendRun` on the pinned transport (read-text, stat, download, upload of exactly that path; never another path, a rename or a listing), only while the session stays in that workspace on the same transport. Save As elsewhere is refused on both save paths (`remoteSaveDestination`, `errWindowSendSaveElsewhere`), the document never leaves the main window (`offer` refuses it with `errWindowSendStays`; the hand-over already treats a terminal binding as ineligible), and a save after the workspace gave the session back says so (`errWindowSendGone`). Known limits: at most 32 such files are open at once (the oldest grant ends first), and the hand-over's "already open" key compares canonical paths, so the same file reached through a mapped drive letter and through its UNC path counts as two files; the workspace's browser stays read-only for everything else, and single-session detached windows and standalone apps do not offer Edit (`TestWindowSendRemoteFileFromADetachedWorkspace`, `TestWindowSendRemoteFileBrowser`).
- Separate programs (docs/SEPARATE_EXECUTABLES.md): `Network_Toolkit_TextEditor.exe` and `Network_Toolkit_Terminal.exe` are the same code as `Network_Toolkit.exe`, built with the `ntk_editor`/`ntk_terminal` tags (`buildEdition`, edition_*.go); never choose a mode from the file name. A separate program opens its app without a switch, keeps that app's switches, refuses the other app's (`applyBuildEdition`), and `Network_Toolkit.exe` keeps every switch and forwards a standalone app to the separate program of its version beside it (`forwardToSeparateProgram`). Start another app only through `standaloneProgram` (separate program, else `Network_Toolkit.exe` with the fixed switch). Detached windows (`--terminal-view`, `--editor-view`) are started through `detachedViewProgram`: the separate program of that app and exact version beside the running one (owner decision: a pop-out shows that program's icon and taskbar name but stays connected to the engine that opened it) when only this user and the system can change it and its folder (`editorRegWritableByOthers`), held open read-share-only from the check until it started; else the running program when it is the main program, else `Network_Toolkit.exe` beside it; always the running program on Linux. The view token stays on stdin. `applyBuildEdition`: the Text Editor program accepts only `--editor-view` and the Terminal program only `--terminal-view`, and a view never also opens the standalone app. Locks, records, peer send and data stay keyed by the data root, never by the program. Their resources live in `internal/winres/<edition>` (index 0 is a named `APP` group; `cmd/network-toolkit/resource_windows_amd64.syso` must stay byte-identical for the main program, whose icon indexes registrations name); `build.sh`/`BUILD_WINDOWS.cmd` build them with an overlay that leaves the main resource out. The Update ZIP keeps the four members released updaters read (they ignore others) and adds the two programs as `Network_Toolkit_<TextEditor|Terminal>_<version>_Windows_x64.exe`; the updater installs all three in one transaction (plan `companions`) or none, and refuses a package without them where they are installed. A copy updated by a helper of 1.21.46 or older gets only `Network_Toolkit.exe`; the new version then adds the separate programs **without asking, only in the start that follows an update the user approved** (owner decision, 2026-11-11: the approval of the update is the consent; `installCompanionsAfterUpdate`). The signal is the one every released helper gives: `--update-health <stage folder>` plus its confirmation in `update-result.txt` (`awaitUpdateCommit`); never download on a plain start, a lone downloaded exe, Linux, or before the helper confirmed. It uses the manual button's verified path (`updateInstallCompanionsFromRelease`), runs once per update (memory only, no saved key), never retries, and on failure leaves the app as it was with the **Install the separate programs** button and the reason. After either path places them, the installed copy's Start menu shortcuts that Setup owns (the `IsOwnedShortcut` rule: `$INSTDIR\Network_Toolkit.exe` with the released arguments, `$INSTDIR` = the uninstall key's `InstallLocation` = the running program's folder) are pointed at the separate programs with no arguments and icon 0 (`updateRetargetCompanionShortcuts`); a shortcut that points elsewhere or that the user changed is never touched. Only when the uninstall key's `DisplayVersion` (written only by Setup, so the version of `Uninstall.exe`, which an in-app update never replaces) is a strict `x.y.z` of at least `companionShortcutUninstallerVersion` (1.21.47): an older uninstaller removes only shortcuts that start `Network_Toolkit.exe` and would leave retargeted ones behind, so those wait for the next Setup (`startMenu: "next-setup"`). The automatic install holds `networkBusy` like the manual button; the status reports `pending` from the start of a qualifying run, and the page hides the button and polls while pending or running. Setup checks that no program is open before replacing or removing any, places the separate programs first, and its file and link registrations still start `Network_Toolkit.exe`. The Linux edition ships only the main program.
- Standalone apps (`--editor-standalone`, `--terminal`; `web/assets/standalone-apps.js`, checked by `scripts/standalone-apps.browser.cjs`): nothing visible that does nothing, and nothing from another tool unless it connects to the other standalone app (Send to terminal, Send to Text Editor). Hide what can never work there instead of showing it disabled. A new palette command, help row, settings section or cross-tool button needs a decision for each standalone app. Local Windows shells are part of the standalone Terminal: Command Prompt and PowerShell on the Start a terminal card, in the connection form, in saved and recent connections, with starting folder and Run as administrator, must behave exactly as in the main window (that card is built once, so anything on it that depends on `/api/status` must be refreshed by `refreshTerminalWelcome()`). The main window and detached child windows must not change.
- New saved UI settings must survive a restart: `mergeState` in web/index.html (or the module's `mergePreferences`) has to restore the key, and keys with a Go sanitizer (`transferClientLayout`, `transferServerSidebar` in transfer_client_settings.go) must allow the new field. The Text Editor sidebar preferences were silently dropped until v1.21.3 for this reason.
- Text Editor session restore (`restoreSession` in `editorPreferences`, default on): only the primary workspaces (main window, standalone Text Editor) keep a session, in `Network_Toolkit.editor-session/` beside their settings (editor_session.go, editor-session.js); detached editor windows never save or restore one, and the renderer uses it only when `/api/status` reports `editorSessionAvailable`. The index holds metadata only, never text, bindings or credentials. Kept copies of disk-backed documents are streamed by Go from a buffer snapshot (`source:'buffer'`), never sent through the renderer, and have no size ceiling. App/window close keeps the session before prompting and asks only about documents that could not be kept; tab close and Close editor prompt as before. **A document opened from outside is the active tab** (a launch request: `--open-file` at start or handed over to the running window; also a file or text from another tool, or a tab the user chose): the restored "which tab was active" applies only when nothing was asked to be opened. The launch file and the session read start together and finish in either order, so never decide this by timing: `noteAsked` in file-editor.js remembers the request until the session is back, kept tabs then reopen behind it (`behind` in `open()`), and `finishSessionRestore` activates it, also when it is itself one of the kept tabs. Every kept tab and its unsaved text still reopens. `TestEditorSessionBrowserOpenedFileIsActive` and the last part of scripts/editor-session-restore.browser.cjs check each start order. Storage moves stream the session (storage_editor_session.go); deleting app data removes it.

## Build and test
Use the repo's existing scripts and vendored dependencies:
- Icon manifest checks require the exact committed SVG bytes. Windows checkout line-ending conversion can change their checksums; preserve LF for `assets/Network_Toolkit_Icon.svg` and `assets/source/Network_Toolkit_Icon.original.svg` instead of regenerating the published icon.
- go test -mod=vendor ./...
- To check that the app compiles, use go build -mod=vendor -o /dev/null ./cmd/network-toolkit (or go vet). A bare go build ./cmd/... writes a 25 MB ./network-toolkit binary at the root; it is in .gitignore and must never be committed (it once slipped into a PR via git add -A). Browser tests run locally write screenshots and reports to ./test-results/ (also ignored); stage files by name instead of git add -A.
- node --test scripts/*.test.cjs
- python3 -m unittest discover -s scripts -p '*_test.py'
- python3 scripts/github_release.py validate
- python3 scripts/build_windows_resources.py
- sh ./build.sh

Native Explorer drag tests must not release the mouse after a fixed delay. The page arms the native copy only when the pointer leaves the source window, which on the hosted 1024px screen happens on the last travel steps. `native-terminal-sftp123.ps1` therefore releases only after the native drag trace reports Explorer's COPY feedback (`Wait-NativeDropAccepted`; the child is built with `toolkit_native_drag_trace122`). If a native drag ends with outcome `cancelled` and no `materialize`, the release came before OLE admission. It does not mean Explorer copied slowly.

Browser tests that list or compare a form's controls must wait until the form has stopped changing: `input-clear.js` (Clear buttons) and `dropdowns.js` (Show all choices) add their buttons on the animation frame after the form appears, so a list read at once may or may not include them (`connectForm()` in `scripts/standalone-apps.browser.cjs` shows the wait).

Setup uninstall checks (`scripts/installer/verify-windows.ps1`): an NSIS uninstaller copies itself to a temporary folder, starts that copy and exits at once. Run it with `Invoke-Uninstaller` (only the in-place `_?=` run uses `Invoke-Silent`) and keep its order: read the launcher's exit state first, then list its child processes (the other order can report "finished" while the copy still works). `Assert-UninstallFinished` names the cause when the program file is still there (refused, copy still running, open program, or a delete Windows completes later); it fails in every case, so do not turn its wait into a pass. Silent Setup and Uninstall show no message: every refusal goes through `StopSetup` in `scripts/installer/windows.nsi`, and a failed install names its step in `$FailedStep`, both written to `%TEMP%\Network_Toolkit_Setup.log` (message only, never a path or name; removed at the start of each run). `Invoke-Silent` prints that reason on an unexpected exit code and checks it on expected refusals, so give a new refusal a `StopSetup` text and a new install step a `$FailedStep` name. Staged files are moved into place with `PlaceStagedFile`, which retries sharing and access errors for about five seconds.

Where fixtures/browser/native host tests need platform-specific setup, run the established .github/workflows/checks.yml jobs in hosted GitHub Actions. Checks runs twice for a pull request from a branch in this repository (push and pull_request events); merge only when both runs are green, re-running a failed job rather than relying on the other run. Never claim physical Windows or live-device acceptance from synthetic tests.

## Release procedure
1. Inspect the current main branch, release notes, handoff, tags, CI and updater channel.
2. Make one reviewed beta per approved UX phase, with relevant behavior/data regressions and screenshots.
3. Record status and known limitations in concise handoff; keep technical CI evidence in an appendix.
4. Run release guards and required CI, never silence genuine security/data failures.
5. Publish via the existing guarded .github/workflows/release.yml process only after the phase is approved.
6. Verify source/tag, the executable, portable and updater ZIPs, SHA256SUMS, update-feed selection and stable-channel isolation.
7. Never replace a published release or change saved state and authorization boundaries.

## Owner approval gate
Phase 0: docs only, no release. Phase 1: audit all tools at 1280×800 and 1920×1080 in light/dark, document consolidations/settings/confirmations/discoverability, and **stop**. Implement Phases 2 to 6 only after owner approval; after Phase 6 establish docs/UI_GUIDELINES.md and freeze layout pending owner approval for later moves.

## Repository standards (all contributors and AI tools)

This repository follows the shared TechSavage1989 standard in [`docs/REPOSITORY_STANDARDS.md`](docs/REPOSITORY_STANDARDS.md), the same file in every app repository. Read it before changing anything. In short:

- **README:** centered header (real icon, one `<h1>`, tagline, quick links Download · Get started · Features · Screenshots · Updates · Development, hero image), then the standard section order. Update it in the same pull request as any user-visible change.
- **Screenshots:** real captures with fictional data in `docs/images/` (`hero.png` + kebab-case names). Recapture any screenshot a UI change makes stale, in the same pull request.
- **Layout:** compact root; respect the root allowlist and checks above. Never commit build output, binaries, archives, logs, caches or secrets.
- **Branches:** short-lived `feat/` `fix/` `docs/` `chore/` `release/` branches, one focused change per pull request, merge only on green checks, delete the branch after merging. AI sessions cannot delete branches through their GitHub access, so `.github/workflows/delete-merged-branches.yml` does it after every push to main: it deletes branches whose pull request was merged (tip unchanged) or that main already contains and are over a day old, never the default, protected or open-PR branches, and lists kept branches with unique commits in its run summary. To remove unmerged branches the owner has approved, start it from this session with `gh api -X POST repos/TechSavage1989/network-toolkit/actions/workflows/delete-merged-branches.yml/dispatches -f ref=main -f 'inputs[branches]=<names>'` (default, protected and open-PR branches are refused; each deleted branch's last commit is logged for restore). Don't ask the owner to delete branches by hand.
- **Instructions:** this file is the single source of project rules for every tool; `CLAUDE.md` imports it. Add new rules and gotchas here.

Where this file's project-specific rules differ from the shared standard, this file wins; an enforced check script wins over both.
