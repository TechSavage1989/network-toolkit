# Network Toolkit standing instructions

## Authority and scope
Read [docs/UX_POLISH_PLAN.md](docs/UX_POLISH_PLAN.md) first. It is the owner's authoritative UX plan; follow [docs/DEVELOPMENT_ROADMAP.md](docs/DEVELOPMENT_ROADMAP.md) for phase status. Historical plans in docs/archive/ are not active requirements. Read docs/DEVELOPMENT_HANDOFF.md for current progress.

**Never prepend release records to AGENTS.md or README.md.** Keep release history in CHANGELOG.md and per-release technical evidence in docs/releases/ or existing docs/RELEASE###_HANDOFF.md files.

## Working with the owner
- The owner has given standing approval to publish new betas when their required release checks pass. Proceed through publication and verification without asking for release confirmation again.
- When the owner's input or decision is needed, when a release has been published, or when work is waiting on the owner, start that message with a bold, clearly marked line (for example **⚠️ ACTION NEEDED:**, **✅ PUBLISHED:** or **⏳ WAITING ON YOU:**) so it cannot be missed (owner request, 2026-11-07).
- End every message to the owner with a clear status: what is done or published, what is running and roughly when it finishes, and what (if anything) the owner needs to do (owner request, 2026-11-07).
- Terminal settings modeled on MobaXterm are planned in [docs/TERMINAL_SETTINGS_PLAN.md](docs/TERMINAL_SETTINGS_PLAN.md).

## Owner's non-negotiables
- Text Editor scalability (owner clarification, 2026-11-08): work effectively with text files of any size while keeping interaction and the rest of the app responsive. Fixed 16/32 MiB file and 30,000-line limits do not meet this requirement. Follow `docs/EDITOR_SCALABILITY_PLAN.md`; do not publish the current bounded-file candidate as completing it.
- Never lose credentials, vault entries, saved profiles, preferences, macros, unsaved work or active sessions. Migrate settings explicitly.
- Preserve Windows/UAC authorization, Hosts/IP/adapter review, explicit download and install consent, and checksum verification. One owner-approved exception (2026-11-11): the start that follows an update the user approved adds that same version's separate Text Editor and Terminal programs without another question (see Separate programs below).
- Never modify or overwrite previously published tags, releases or binary assets.
- Never access the owner's actual network devices, desktop or files. Use fixtures and hosted CI.
- Redesign, consolidate and rename controls when owner-approved; preserve actions and data.
- Native minimum dimensions in Phase 2: main 960×600, detached Editor/Terminal 640×400.
- The old 390px Editor comparison-motion drift test and its 2px threshold are retired. Narrower widths are unsupported; use behavior/data tests and screenshot review instead of pixel-specific cosmetic gates.
- No application-code changes in Phase 1. After the UX audit, **stop for explicit approval** before implementation.
- Work in 1.18.x betas, one per approved implementation phase (2 through 6).
- Update checks must eventually run at startup and every six hours, with manual checking and explicit user approval to download/install retained.
- Keep What's New short, plain-language and focused on the experience; technical detail belongs under Additional Details. The updater shows every What's New item in full (owner request, v1.21.5), so keep the list to a few clear sentences.

## Repository layout
- cmd/network-toolkit/: Go application and Windows native host; internal/: platform, network operations, security, Terminal and transfer logic.
- web/: UI sources; assets/ and themes/: resources; scripts/: tests, generators and release tooling.
- docs/guide/: user-facing topic guides; docs/releases/: archived release notes; docs/archive/: superseded plans; docs/RELEASE###_HANDOFF.md: historic engineering handoffs.
- Keep root documentation concise, with at most one latest-beta reference in README.

- Dropdowns (v1.21.10): `web/assets/dropdowns.js` converts every `<input list="…">` into an app-styled combobox and removes its `list` attribute (kept as `data-combobox-list`), so never rely on `input.list`. Selects stay native while closed and switch to the app-colored list (`.ntk-picker`, base-select) only while open; do not style closed selects with `appearance: base-select`, because it changes their size and CI compares layouts with pinned older builds.
- Toggle buttons (owner rule, after v1.21.54: "buttons that open a new row of menu items, like Find, should be a toggle and should close the new row … instead of needing a dedicated hide or close button"): a button that reveals an inline row, bar, strip, sidebar section or panel is a toggle. Pressing it again closes what it opened, its keyboard shortcut toggles too (Escape in the row may also close it), and it carries `aria-controls`, `aria-expanded` and the class `reveal-toggle` (panel-controls.css: the `.btn.selected` look while open). Never add a separate Hide/Close button for such a row or panel. Keep a close control only for a panel that opens without a button (a details pane opened by selecting a device, packet or result keeps its collapse chevron, which is itself the toggle) and for dialogs (`role="dialog"`, modal or not); a panel that opens over the page must not cover its own toggle. Menu entries that open a row (a tab menu's Find) only open it. Examples: Terminal Find and Command bar, local shell Browse…, Hosts Find / replace and Validation, packet Insights, What to look for and Colors & maps, File Transfer server settings rail, client Connection settings and the server copy dialog's Browse local files.

The Syntax highlighting picker and the preview are pinned together (`.terminal-preview-sticky`, built in `mount()` of terminal-appearance.js); settings that change how output looks go below it so the preview shows their effect. Put a new terminal option in the matching tab (`[data-terminal-settings-panel="…"]`, or mark markup in `terminalToolsHTML()` with `data-terminal-settings-target`); never add app-level buttons (theme, app settings) to it. The Tools menu is gone (v1.21.18): `#terminalToolsPanel` is only a hidden staging container that terminal-extras.js empties into the active-session bar and the Settings tabs. Connection tools belong in the Saved sidebar (footer: Password manager, SSH host keys), not in a new toolbar menu. Separate terminal windows show theme, window settings and help at the bottom of the terminal sidebar rail (`terminalAppToolsHTML()`), not in the toolbar: the toolbar must stay one row in a 1024 px terminal window, because app-chrome109 compares that window's terminal height with 1.17.108 and CI's fonts are wider than local ones.

In a standard process Windows' approval starts the private helper (`--terminal-shell-helper`, `openElevatedTerminalShell`, terminal_shell_protocol.go) that runs the shell and relays it; in a process that already runs as administrator the shell is a direct child (`openAdministratorShell`). Restart as administrator (`/api/admin-restart`, `admin_restart.go`: a visible `runas` start with `--admin-reopen <pid> <folder>` first, which waits before anything else until the old process exits, then the page's normal `closeApp()`; a kept-open app sends `cancel`; main window and standalone Terminal only, never with popped-out windows of this engine open) is offered only when an administrator tab could not start for a reason other than a declined approval (`[data-terminal-admin-restart]` in the connection form). `TestAdmin*`, `TestTerminalShell*` and `scripts/terminal-local117.browser.cjs` check it.

The page's strength gauge (`vaultStrength`) is a port of `estimateVaultPasswordStrength`: change both and the shared vectors (`TestVaultStrengthVectors`, scripts/connection-credentials.test.cjs).

Only the user's own pastes pass `own` to `acceptText` (the clipboard read of `paste()` and the native paste event); `pasteText`, used by Send to terminal, window send and peer send, never adds an Enter (the "no automatic Enter" rule of those paths). `scripts/terminal-pager.browser.cjs` checks both paths with real input.

- Terminal links (`ssh://`, `telnet://`, `serial:`): `cmd/network-toolkit/terminal_link.go` is the only parser and `--terminal --open-url "<link>"` the only command (no other switch is accepted with it, so a quoted link cannot add arguments). A link only prefills the connection form (`web/assets/terminal-links.js`): never auto-connect, never take a password from a link, never pick a credential, host key or profile without the user. Setup (`scripts/installer/windows.nsi`) registers per user via Capabilities\URLAssociations, never writes a UserChoice, and creates a scheme key only when neither HKCU nor HKLM has one (recorded under `Software\Network Toolkit\Terminal\CreatedSchemes` so uninstall removes only those). Links stay in the in-memory request inbox: never save them in settings, and keep `--open-url` out of `updateRestartArgs`. The Linux edition has no standalone Terminal menu entry, so it registers no link handler.
- Text Editor as a Windows default: `scripts/installer/text-extensions.nsh` is the **one list** of file types Setup offers the Text Editor for. `windows.nsi` includes it, `verify-windows.ps1` reads it, and the list in docs/guide/editor.md is generated from it (`node scripts/text-extensions.cjs --write`); `scripts/text-extensions.test.cjs` fails when they differ. Add only formats that are text by definition (no documents, images, archives, programs, or names that are sometimes binary), and never remove a type a released Setup registered. Setup only **offers** the editor, per user (HKCU): never write a `UserChoice` or anything under `FileExts`, never write the default value of an extension, never change a key another program wrote. The keys (documented in the comment above `APPLICATION_KEY` in windows.nsi): `RegisteredApplications` + `Capabilities\FileAssociations` (Default apps), the ProgID as a value of `<.ext>\OpenWithProgids` (Open with for known types), `Classes\Applications\Network_Toolkit.exe` with `shell\open\command`, `FriendlyAppName` and `DefaultIcon` (Open with for **any** file; no `SupportedTypes`, which would hide the editor for unknown types; written only when the key is absent or already starts the installed program), and the optional `Classes\*\shell\NetworkToolkit.TextEditor` verb (Setup box or `/ContextMenu`, off unless chosen, remembered in the uninstall key like the desktop shortcut; `/NoContextMenu` removes it and the remembered choice in a silent setup, and the two switches together are refused through `StopSetup`). Every command is `${EDITOR_COMMAND}`: `"%1"` is the one quoted value of `--open-file`, or the one bare path Windows' own Open with entry passes (when the user browses for a program in "Choose another app", Windows writes `Applications\<program>\shell\open\command` = `"<program>" "%1"` itself), and the app accepts nothing else beside it: `applyOpenWithArgument` (editor_launch.go) reads a lone bare path as `--editor-standalone --open-file "<path>"` in `Network_Toolkit.exe` and the Text Editor program, refuses it beside any switch, after `--`, as two or more arguments or with switch syntax (a leading `-`, or on Windows a leading `/` that is not `//server`), and the Terminal program refuses it; `updateRestartArgs` turns it into `--editor-standalone` (`TestOpenWithArgumentPerEdition`). Keys Setup created where another program's key could already be (`.ext`, `.ext\OpenWithProgids`, `*`, `*\shell`, `Applications`) are recorded under `Software\Network Toolkit\TextEditor\CreatedKeys`; uninstall and a rolled back install remove only those, through `DeleteEmptyUserKey` (never `DeleteRegKey /ifempty`, which ignores values). Setup up to 1.21.43 kept no record: the first upgrade from it (`TextEditor` key absent) adopts the five released types' keys with `AdoptReleasedExtension`, only where a key holds nothing but our ProgID; never widen that to other types or later upgrades, because a key another program created and left empty looks the same. The registry provider treats `*` as a wildcard: the hosted check reads those keys with `Get-UserKeyTree`/`Read-UserValue` (.NET). Icons (`EDITOR_ICON`/`DOCUMENT_ICON` in windows.nsi) are zero-based icon group indexes in the order of `ICON_GROUPS` in scripts/build_windows_resources.py: 0 app, 1 Text Editor, 2 Terminal, 3 text document (owner request, 2026-11-11). Values that stand for the program use 1: `Capabilities\ApplicationIcon` (Default apps), the right-click verb's `Icon`, and the `Icon` value of `shell\open` of `Applications\Network_Toolkit.exe` (Open with; never on Windows' own `Applications\Network_Toolkit_TextEditor.exe`) (the Start menu shortcuts of the Text Editor and the Terminal start the separate programs and use their own index 0, the `APP` group). A file's icon uses 3: the ProgID's `DefaultIcon` **and the `DefaultIcon` of an `Applications\<program>.exe` entry**. Explorer shows the `DefaultIcon` of the key the type's UserChoice names as the icon of the file, and choosing the editor in Open with or Default apps can name `Applications\Network_Toolkit.exe` (or Windows' own `Applications\Network_Toolkit_TextEditor.exe`) instead of the ProgID; an entry without `DefaultIcon` shows its program's first icon (owner report on 1.21.51: files set to the editor showed the editor tile). Evidence (learn.microsoft.com is blocked in cloud sessions; the doc sources are in MicrosoftDocs/win32 on GitHub): *Verbs and File Associations* (`desktop-src/shell/fa-verbs.md`, "Register an Application to Handle Arbitrary File Types") says the keys under `Applications\<program>.exe` define a file type's characteristics "such as the shortcut menu items and the icon. If a user associates your application with an additional file type, that class will have these characteristics" and "If you include a DefaultIcon subkey, then you should use a generic icon"; *Application Registration* (`app-registration.md`) calls it an icon "instead of the first icon stored in the .exe file"; Visual Studio Code's Setup (`build/win32/code.iss`) writes its document icon to `Applications\Code.exe\DefaultIcon` and the program's own icon only on the open verb. Default apps shows a registered program by `ApplicationIcon` (de facto: the Default Programs doc no longer lists it; without it Windows uses the program of the first ProgID). Which value Open with reads for the program is not confirmed on Windows 11 (ReactOS's Open with, `COpenWithMenu.cpp`, extracts icon 0 of the program and ignores `DefaultIcon`), so the entry also carries the program icon on its open verb, as Visual Studio Code's does: Setup and the portable registration write `shell\open` `Icon` = `EDITOR_ICON` wherever they write that entry (also when they take over an entry Windows wrote for the same program), it goes with the entry's other values (Setup's `RemoveApplication` deletes the key; the portable Remove deletes the value), and the post-update repair adds it under the same guard as the entry's `DefaultIcon`. Check Open with on real Windows after a change. The document icon is rewritten by every install and upgrade (1.21.44 and earlier wrote 1 to the ProgID, 1.21.51 and earlier 1 to `Applications\Network_Toolkit.exe`), by the portable registration, and by the first start after an in-app update (`editorRegRepairDocumentIcon` through `planEditorIconRepair`, all reads first: the ProgID's value when its `shell\open\command` starts the running `Network_Toolkit.exe`; `Applications\Network_Toolkit.exe` (its `DefaultIcon` and its open verb's `Icon`) only when its command is the Text Editor command of the running program, never an entry Windows wrote with the bare file name, which nobody would take back; then `SHChangeNotify`; never a key of another program). **An icon the user set on that entry stays**: the repair writes its `DefaultIcon` only when it is absent or exactly what 1.21.44 to 1.21.51 wrote (`"<program>",1`) and the verb `Icon` only when absent; the portable registration, registering again or taking over, writes each only where it is absent or a registration's value (`editorRegWrittenIcon`: the editor or document icon of this copy or the replaced one). Setup still rewrites its own entry whole (name, both icons, command) on every install and upgrade, as it always did, so a user icon there lasts until the next Setup; Setup's uninstall and the portable Remove take the whole entry back. Windows' own `Applications\Network_Toolkit_TextEditor.exe` (written when the user picks the separate program in Open with: a command, no icon) is never created (a second entry would list the editor twice) and its command is never changed: when it starts the Text Editor program beside the installed or the registered portable `Network_Toolkit.exe` and has no `DefaultIcon` key, or holds the recorded value or exactly the document icon, the registration writes `"<dir>\Network_Toolkit.exe",3` (`RegisterEditorApplicationIcon`, `planEditorAppIcon`; in Setup this step is never fatal: a failed write is skipped and not recorded, and never rolls back an install or stops an upgrade, `TestSetupEditorApplicationIconIsNotFatal`) and records the value as `EditorApplicationIcon` in its record (Setup's `Software\Network Toolkit\TextEditor`, or the portable record; `AdoptPortableRegistration` carries the portable value over). Uninstall, Remove and Clean up delete that value only while it still equals the record, then its `DefaultIcon` key once empty (`RemoveEditorApplicationIcon`, `planEditorRemoveAppIcon`); an icon anyone else set, or an icon key someone else created, is never touched. The post-update repair writes it for the registered portable copy, and for the installed program only when the installed uninstaller (`DisplayVersion`) is at least `editorRegEditorAppIconUninstallerVersion` (1.21.52, the first release with `RemoveEditorApplicationIcon`; `TestEditorAppIconUninstallerVersion` checks that it is no newer than `model.Version` and that `UnregisterShell` holds the removal): an older uninstaller would leave it behind, so the next Setup writes it. Known limits: the gate trusts `DisplayVersion` as the uninstaller's version (only Setup writes it; a hand-edited value could let the repair write an icon the uninstaller keeps). A version older than 1.21.52 does not know `EditorApplicationIcon`: an older Setup taking over a newer portable registration does not adopt it and deletes the portable record, so that icon stays in Windows' entry after uninstall; an older portable copy cleaning up a newer copy's registration leaves the value and the record key holding it; an older portable copy registering again, or an older Setup installing over a portable registration, writes the editor icon (1) as the entry's `DefaultIcon` and no verb icon, until the next newer registration, Setup or post-update repair. Released Setups and shortcuts name 0 to 2, so never reorder or remove a group: append new ones (`scripts/windows_resources_test.py` checks this). The document icon is the editor icon's sheet without its tile (`assets/source/Network_Toolkit_Document.svg`, with pixel-grid drawings `Network_Toolkit_Document.<16|20|24|32>.svg` for the small sizes); regenerate it with `python3 scripts/generate_icon_assets.py --document` (Inkscape), which never touches the published icons, then `python3 scripts/build_windows_resources.py`. Its sources and ICO are pinned in `assets/Network_Toolkit_Document.manifest.json`.
- Portable Text Editor registration ("Use this copy's Text Editor in Windows", App settings → Editor of the Windows main window; `cmd/network-toolkit/text_editor_registration.go`, page `web/assets/windows-integration.js`): every rule of the bullet above applies. On the user's click only (never at startup; the startup check only reads and offers **Clean up** for a registration whose program is missing), the portable copy writes Setup's keys and values for itself, with `editorRegCommand(exe)` (`${EDITOR_COMMAND}`'s shape), the editor icon for `ApplicationIcon`, the right-click verb and the open verb of its Applications entry, and the document icon for the ProgID, the `DefaultIcon` of its Applications entry and Windows' own entry of the separate Text Editor program beside it, for the types in `textEditorExtensions`, which `node scripts/text-extensions.cjs --write` generates from text-extensions.nsh (`scripts/text-extensions.test.cjs` and `TestEditorRegistrationMatchesSetup` fail when Go and Setup differ). Its record is `Software\Network Toolkit\PortableTextEditor` (`Executable`, `ContextMenu`, `EditorApplicationIcon`, `CreatedKeys` named like Setup's), written before the keys; a key is recorded only when this registration created it, and Remove deletes values it wrote and then keys only through `editorRegDeleteEmpty` (the Go port of `DeleteEmptyUserKey`; `DeleteKey` never deletes a tree). Plans are computed from reads through the `editorRegistry` interface (tests use an in-memory registry), a read error writes nothing, and each action holds Setup's mutex `Local\NetworkToolkitSetup` and ends with `SHChangeNotify(SHCNE_ASSOCCHANGED)`. Ownership: **the installed program wins** — while the uninstall key names an `InstallLocation`, a portable copy refuses register, takeover and remove and says so. **Setup takes a portable registration over**: `AdoptPortableRegistration` copies the portable `CreatedKeys` into Setup's before the types are registered, `RegisterApplication` rewrites an `Applications\Network_Toolkit.exe` entry that starts the recorded portable program, `.onInit` preselects the right-click box when the portable record has `ContextMenu` (cleared, Setup removes the entry), and `RetirePortableRegistration` deletes the portable record after Setup's registration is written; uninstall then removes everything as Setup's own (a rolled back install leaves the portable record, whose copy then reports an incomplete registration to repair). **One portable copy at a time**: another copy (or an unrecorded registration) is replaced only with `takeover` after the user confirms; the record and its `CreatedKeys` carry over. The program file must be named `Network_Toolkit.exe`. Register and takeover are refused (`errEditorRegPercent`, `errEditorRegUnsafe`, through `editorRegStatus`) when the program path holds a `%` (Explorer expands `%1`/`%L` inside the program path too; Setup's `ValidateInstallDirectory` refuses such a folder through `StopSetup`) or when anyone but this user, SYSTEM, Administrators or TrustedInstaller can change the program or its folder (`editorRegWritableByOthers` reads the owner and DACL; every double-clicked text file would run that copy). Remove is for this copy's own registration only; another copy's registration is cleaned up only through `/text-editor/cleanup` with the `owner` the page showed, refused (`errEditorRegStale`) unless the registration still names it and that program is confirmed missing. A program whose drive or share is not connected (or could not be checked) is `ownerUnreachable`, never missing (`editorRegClassify`), and offers no clean up. The hidden switch `--text-editor-registration=register|register-menu|takeover|takeover-menu|remove|cleanup` (alone only; exit 0 done, 2 failed, 3 installed program, 4 another copy, 5 file name, 6 nothing of this copy's or nothing to clean up, 7 location refused) exists for the hosted check, which runs portable register/remove (all of `HKCU\Software\Classes` but `Local Settings` compared), two copies with takeover and cleanup, portable then Setup, and Setup then portable.
- Install the full version (App settings → Updates of a portable copy; `cmd/network-toolkit/full_install.go`): finds `Network_Toolkit_<version>_Windows_x64_Setup.exe` of the running version through `releases/tags/v<version>` on api.github.com and falls back to the update channel's latest release only when that release or its Setup is missing **and** the fallback is newer (`updateNewer`; `fallback`, `running`, `newer`; the page names both versions). Never offer an older release: it could save over settings a newer version wrote, and its Setup would not take over the portable registration; otherwise say that no installer was found for this version (`errFullInstallNoNewer`). Network access only through `updateFetch`/`updateFetchProgress`/`updateHTTPClient` (the updater's hosts and redirect rule) while holding the updater's `networkBusy` slot; verification only through `updateVerifySum` against that release's SHA256SUMS, in memory, before anything is written; a mismatch writes nothing. Starting needs `{version, confirm:true}` after the download's own `{version, confirm:true}`: the page asks twice (`data-windows-install-confirm`). Downloads never live in the data folder (the user may have put it where others can write): `%LOCALAPPDATA%\NetworkToolkit-Setup\.network-toolkit-setup-<random>\`, both levels created with a protected owner-only DACL at creation (`fullInstallMakePrivateDir`) and accepted only as plain folders nobody else can change (`fullInstallCheckPrivateDir`: no junction or link, `editorRegWritableByOthers` empty). `fullInstallLaunchVerified` repeats those checks, opens Setup once with `FILE_SHARE_READ` only and no reparse following, checks that the handle's final path is the expected one, hashes it from that handle and starts it with `CreateProcess` (no arguments: interactive, never `/S`) while the handle is still open; any failed check refuses to start, and changed bytes delete the download. The start does not hold `fullInstall.mu` (a `starting` flag refuses a second start). Downloads are removed by discard, at exit when never started, and by the next download. `full_install_windows_test.go` proves the owner-only folder, the refused junction and that the held file cannot be written, renamed or deleted while the started program is the verified file. The installed program is found through the uninstall key; "Open the installed program" starts it, "Reinstall or repair anyway" still offers Setup. The data folder note comes from `storage_location.go`: only an explicit `--data-dir` run uses a folder the installed program does not read. The routes `/api/windows-integration/…` exist in the main window only.

After an edit (a new revision) the earlier chunks stay on screen (`old`) until the window's chunks are read again, `SAMPLE_DELAY` later. - Window launch and peer send are two separate uses of a window's activation token (`terminal_window.go`, `peer_send.go`). **Launch** requests (a second start, a link, a file from Explorer) still carry only connection settings or a file to open: never authentication, never terminal input. **Peer send** carries text only, sent only by the standalone Text Editor or the standalone Terminal of one data root, found through the receiver's instance record. The sender's engine picks the receiver in this order and never asks the user to open anything (owner request): the other standalone app if it runs; otherwise the main Toolkit window of the same data root while its page runs (its Terminal page or its Text Editor; `status.peerReceive` starts that page's inbox; a main window whose protected record is valid and whose engine answers but whose page has not polled within `peerTargetsFresh` is probed again for up to `peerMainGrace` (3 s, `peerProbeMain`, bounded by the sender's request) before it is passed over, so a send just after it opened does not start the other app; only the main window gets this, a standalone app counts as running while it starts); otherwise it starts the other standalone app with the existing fixed launch arguments (`launchPeerApp`; never text on a command line) and holds the text in its own memory until that app's record appears and its page is ready, for at most `peerLaunchWait` (25 s, under the server's 30 s write timeout), then delivers it once. A send still waiting when the sender closes is dropped, never saved; on a timeout the user is told and their text stays where it was. Terminal text needs a session the user connected: with none, say so as a send inside one window does, and never connect one. A page shows targets from one receiver and the engine itself sends a session or an open document only to that receiver (`peer.listed`): with nothing listed such a send is refused ("Choose Send to … again"), never routed to whichever app runs. Text goes only to the instance that was just probed: `peerDeliver`/`peerCall` take that instance id and compare it with the record before anything is sent. "Is another send starting?" and recording the new send happen under one lock, so two sends never both start the other app. `launchPeerApp` gives foreground rights only to a process named by a record peer send trusts (`peerForegroundPID`), never from a plain record. The main window only receives text: its own Send to commands never use peer send (they stay inside its engine, below), it sends no text or sessions anywhere, and its child windows never send through peer send. **Child windows reach peer send only through their owner engine** (owner decision, v1.21.50): a detached window of a standalone app's own tool (a Terminal window of the standalone Terminal, a Text Editor window of the standalone Text Editor; `peerChildKind`, `status.peerSend`, `startSender` in peer-send.js) uses its owner's `/api/peer-send/` `targets`, `open`, `send` and `result` with its view token (`handleChildPeerSend`; `inbox`, `report`, `ack` stay the app's own window's), and the owner engine sends with every rule here; `peer.listed` is kept per sending window and a result is read only by the window that sent it (`peerOutbound.from`). No `/api/peer/` route is ever served to a child or reached by one. A receiving engine lists and accepts the sessions and documents of its detached windows too (what they report through window send; `peerInboundTargets`), and text for one of them is queued for that window through window send from `peer` (`peerEnqueue`, `windowSendEnqueueText`; its state is read there), with all of window send's checks. What the app's own page reported counts only while the engine says that window still holds it (`peerPrimaryHolds`: no detached view owns the session, no detached window holds or is taking the document): its page keeps reporting a session it just popped out until its next report, and text must never be queued there (CI finding; `TestPeerSendNeverQueuesAPoppedOutSessionForTheAppsOwnWindow`); a target that moved but whose window has not reported yet is refused with "moved to another window". Browser drivers that play a native child must pulse as promptly as one does (it pulses before its window opens), never once a second. This includes the **main** Toolkit engine (owner decision, v1.21.50, extending "the main window only receives"): its detached Terminal and Text Editor windows receive peer text for the sessions and documents they hold, and a main engine whose main window is closed while a detached window stays open still counts as a receiver for them (`ready` comes from that window; the main window is not reopened for it). The text still goes in only through that window's `pasteText` / `newDocument`/`insertText`/`pickInsert` behind `blocked()` (`TestPeerSendReachesADetachedWindowOfAClosedMainWindow`). Its one sending use is the **document hand-over** (owner decision, `peer_handover.go`, `web/assets/editor-handover.js`): when the user moves main-window editor tabs to a **new** window with Detach editor or Move all (`move(..., {handover:true})`; owner decision: Move to separate window on a single tab always gets its own connected window, and never a tab drag or a child window) while the standalone Text Editor of the same data root runs and its page is ready, local and untitled tabs go to that editor instead; everything else (SFTP/SSH bindings, `Binary`, disk-backed tabs with unsaved changes, formats other than UTF-8/UTF-16 with LF/CRLF/CR, files not on disk yet or changed on disk) goes to a connected window as before, and with no such editor nothing changes. Routes: the main page's `/api/peer-handover/` (`receiver`, `start`, `result`; session token, main window only) and the editor's `/api/peer/documents/` (`status`, `handover`, `result`; same guards as text, kind `documents`, 12 tabs and 8 MiB of text per request, the one pending request shared with text), always pinned to the probed instance (`peerCallReceiver`). **Never lose a tab**: the page freezes the tabs (`snapshot`), and only tabs the editor's page confirmed per tab (`ack` with `items` naming every sent tab once) are released; a refusal, an expiry, a lost receiver or an invalid confirmation gives every tab back (`rollback`), so at worst both windows hold a tab, never neither. The receiving page opens a file only through the ordinary local open (`adoptHandover` in file-editor.js), applies unsaved text only when the file still has the read digest and the format matches, removes what it could not carry exactly (`discardAdopted`, only an untouched tab it created), and with "Reopen files next time" on confirms unsaved text only after `session.save()` kept it. **File paths** travel on this route only (owner-approved exception): absolute local paths (a drive letter on Windows, `/` elsewhere; no UNC, device, network-drive, `.`/`..` or stream path; `peerHandoverLocalPath`), checked by both engines, with a dirty file's digest checked by both (`peerHandoverUnchanged`). **Undo history moves with page-held tabs** (owner decision, v1.21.50): `undo`/`redo` of a tab (at most 80 each, the editor's own limit) count against the same 8 MiB as unsaved text (`validatePeerHandover`); a tab whose history does not fit moves without it, and a disk-backed tab always does (its history lives in the main engine's buffer and cannot be rebuilt exactly elsewhere). The receiving page applies history only onto exactly the text it belongs to (`adoptHistory`: the carried text, or a saved file with the read digest, page-held) and otherwise confirms the tab with `historyLost`; the main window's message names every moved tab that did not keep its history and why. Never drop history silently. Terminal sessions never move to the standalone Terminal. A running app with a plain or unreadable record, or without `/api/peer/` (an older version), is never a receiver: skip it and name it to the user (`peerNote`). That record is protected (DPAPI on Windows for main, editor and Terminal; a private 0600 file elsewhere): never write a plain record, and never trust a plain record for peer send (an older Terminal's plain record may still receive launches). `/api/peer/` (the same routes and guards in the standalone apps and in the main window, which serves both kinds) accepts the activation token only, from loopback only, never from a page, with strict JSON and size limits (1 MiB to a terminal, 8 MiB to the editor), one pending request per window for at most a minute. The receiving page must use the same code as a send inside one window: `pasteText` for the Terminal (paste review, paste warnings, bracketed paste), `newDocument`/`insertText`/`pickInsert` for the editor, and it must never replace an open dialog: `blocked()` in peer-send.js (app dialogs, a native `dialog[open]` such as the colour picker, the editor's Move / merge box, and in the main window a password being typed) is asked before the window changes page and again, as `guard`, immediately before `pasteText`, `newDocument`/`insertText` and `pickInsert`. The sending page follows the same rule: after the automatic open (up to 25 s) `openPeer` shows a message instead of a dialog if another dialog is open by then. Known limit: a main window that registered its record polls its own engine's peer inbox once a second while it is open. Never add credentials, tokens, host keys, file paths (beyond the hand-over's local paths), automatic Enter or command execution to either path, and never show the other app's token to a page.

App/window close keeps the session before prompting and asks only about documents that could not be kept; tab close and Close editor prompt as before. **A document opened from outside is the active tab** (a launch request: `--open-file` at start or handed over to the running window; also a file or text from another tool, or a tab the user chose): the restored "which tab was active" applies only when nothing was asked to be opened. - Scroll cost (owner report on v1.21.61: large files lagged while scrolling, with the Document Map off too; `scripts/editor-scroll-cost.test.cjs`): three rules. **Never put `:has()` on `html`, `body` or `:root`**: it is re-checked on every change anywhere in the page, and every element any `:has()` rule could match is restyled (a line-number redraw restyled over 1,100 elements, several times per scroll step). Keep page-level state as a class on `<body>` set by script (`syncEditorPageState` in file-editor.js keeps `nt-editor-is-embedded` and `nt-editor-sidebar-open`). **Code that runs on scroll or on every redraw writes nothing that did not change** (an attribute set to the same value still costs a restyle): `web/assets/input-clear.js` writes `hidden`, labels and classes only when they differ, reacts to a scroll only when it can move a field that has a Clear button, and ignores the editor's gutter, highlight, measure and map. **Hidden helper elements with many children go in a shadow tree** (`createMeasure` in editor-disk-view.js: the wrap measure's rows inherit font and wrapping from the host and match none of the page's style sheets). Measure before guessing: a Chrome trace (`devtools.timeline` with the `.stack` and `.invalidationTracking` categories) names the selector behind a style recalculation.
- Browser file import (a drop or Open file; **the same size rule as a path open**: over `memoryEditorUnits` (512 KiB) or `memoryEditorLines` (4,000 lines, `moreLinesThan` in `importFiles`) the document is disk-backed. A page-held document draws line numbers and colours for every line at once, so a 350 KB configuration of 12,000 lines stalled on every scroll step until v1.21.63; any new way to open a file must apply both limits; `sendBrowserFile` in file-editor.js, `diskUpload` and `gunzipEditorChunk` in editor_disk_upload.go): the page has no path for such a file, so it sends the bytes to the engine in chunks of at most `editorbuffer.MaxEditBytes` (1 MiB), in order (`import-chunk`, also `verify-chunk`). The upload is the slow part (owner: files up to 100 MB by drag and drop), so a chunk is gzip-compressed with `CompressionStream` when that makes it clearly smaller (`gzip:true` on the request; plain otherwise, and both may be mixed), and chunks are read and compressed four ahead while they are sent in order. The engine expands a compressed chunk before anything else looks at it and refuses one that is not gzip, is empty, or expands past one chunk, so a small request can never fill memory (`TestGunzipEditorChunkIsBounded`, `TestDiskEditorImportsCompressedChunks`). Never raise the chunk past `MaxEditBytes` or accept a compressed stream without that bound.

SSH sign-in notices: the per-connection/profile boolean sshAutoContinueNotices defaults on for new SSH connections and missing saved choices. ## Release procedure

## Repository standards (all contributors and AI tools)

This repository follows the shared TechSavage1989 standard in [`docs/REPOSITORY_STANDARDS.md`](docs/REPOSITORY_STANDARDS.md), the same file in every app repository. Read it before changing anything. In short:

- **README:** centered header (real icon, one `<h1>`, tagline, quick links Download · Get started · Features · Screenshots · Updates · Development, hero image), then the standard section order. Update it in the same pull request as any user-visible change.
- **Screenshots:** real captures with fictional data in `docs/images/` (`hero.png` + kebab-case names). Recapture any screenshot a UI change makes stale, in the same pull request.
- **Layout:** compact root; respect the root allowlist and checks above. Never commit build output, binaries, archives, logs, caches or secrets.
- **Branches:** short-lived `feat/` `fix/` `docs/` `chore/` `release/` branches, one focused change per pull request, merge only on green checks, delete the branch after merging. AI sessions cannot delete branches through their GitHub access, so `.github/workflows/delete-merged-branches.yml` does it after every push to main: it deletes branches whose pull request was merged (tip unchanged) or that main already contains and are over a day old, never the default, protected or open-PR branches, and lists kept branches with unique commits in its run summary. To remove unmerged branches the owner has approved, start it from this session with `gh api -X POST repos/TechSavage1989/network-toolkit/actions/workflows/delete-merged-branches.yml/dispatches -f ref=main -f 'inputs[branches]=<names>'` (default, protected and open-PR branches are refused; each deleted branch's last commit is logged for restore). Don't ask the owner to delete branches by hand.
- **Instructions:** this file is the single source of project rules for every tool; `CLAUDE.md` imports it. Add new rules and gotchas here.

Where this file's project-specific rules differ from the shared standard, this file wins; an enforced check script wins over both.
